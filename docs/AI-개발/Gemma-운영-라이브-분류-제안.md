# 제안: 운영에 Gemma 4를 올려 두고 '라이브 분류' 버튼으로만 실행

상태 **제안 초안 (팀 검토 전)** · 작성일 **2026-09-29** · 제안 최은지 · 관련 [Gemma 로컬 편집 결정](Gemma-로컬-편집-엔진-결정.md) · [Plan 03 리스크](../plans/03-term-risk.md) · [Plan 05 배포](../plans/05-trend-cloud-run-deployment.md) · [Plan 06 로컬 편집](../plans/06-gemma-on-cloud-run-gpu.md)

## 요약

- 운영에 Gemma 4 서비스를 **올려 두되** 정기 수집·분류는 돌리지 않는다. 평소에는 꺼져 있다(인스턴스 0).
- 사전 항목에 **'지금 다시 분류해 보기'** 버튼을 둔다. 누르면 그 용어 하나만 최신 기사 문장을 모아 Gemma가 분류하고, 파이프라인과 같은 규칙으로 리스크를 판정해 **수집 서버 배치 결과와 나란히** 보여 준다.
- 결과는 화면에만 보여 주고 공개 사전에 쓰지 않는다. 비용은 하루 실행 횟수로 묶고, **Cloud Run 지출 한도가 웹·API까지 멈추지 않게** Gemma를 따로 떼어 둔다.

이 제안은 [Gemma 로컬 편집 결정](Gemma-로컬-편집-엔진-결정.md)의 "Cloud Run GPU는 지금 배포 대상이 아니다"를 일부 되돌린다. 그 문서의
재검토 조건(실시간 Gemma 호출의 사용자 가치, 품질·지연·처리량·비용 실측)을 아래 7절에 맞춰 두었다.

## 배경

| 현재 결정 | 이 제안에서 |
| --- | --- |
| Gemma 실험·편집은 팀원별 Kaggle 노트북 GPU, 수집과 대체 추론은 수집 서버(PC)의 배치에서 돈다([Plan 06](../plans/06-gemma-on-cloud-run-gpu.md), 2026-10-01 Colab에서 변경). 운영 웹·API는 `USE_LOCAL_GEMMA=0` | 유지. 배치·실험 위치는 그대로다 |
| 운영에 파이프라인 Job·Scheduler를 두지 않는다 | 유지. 자동 실행은 없다 |
| Cloud Run GPU Gemma를 배포하지 않는다 | **변경.** 버튼으로만 켜지는 GPU 서비스 하나를 둔다 |
| 운영 DB에는 검증·검수된 결과만 게시한다 | 유지. 버튼 결과는 공개 사전에 쓰지 않는다 |

바꾸려는 이유는 심사다. 심사위원은 배포된 서비스를 직접 쓴다. 지금 구조에서는 Gemma가 만든 결과(리스크 분류, 적합도 태그, 언어판)는
보이지만, **Gemma가 돌아가는 순간**은 영상에서만 보인다. 기술 배점(40%)의 "생성형 AI의 의미 있는 활용"과 "기술적 구현"을
배포본 안에서 직접 확인하게 하려는 것이다.

## 제안

### 1. 버튼을 누르면 일어나는 일

| 순서 | 하는 일 | 모델 |
| --- | --- | --- |
| 1 | 운영 Gemma 서비스를 깨운다. 화면에 "Gemma를 준비하는 중"과 경과 시간을 보인다 | — |
| 2 | 그 용어로 Google 뉴스 RSS를 조회해 최신 기사 제목을 모은다(`collectors/news_rss`, 키가 필요 없음). 표제어가 실제로 든 문장만 남긴다(`match.mentions`) | 없음 |
| 3 | 문장마다 뉘앙스·위험 유형·그 뜻으로 쓰였는지를 붙인다. 프롬프트·출력 형식·재질문은 `pipeline/risk.py`와 같다 | **Gemma 4** |
| 4 | `risk.judge`와 같은 문턱으로 수준을 정한다(사용 자제·주의·없음·판단 보류) | 없음(규칙) |
| 5 | 결과를 수집 서버 배치의 수준·이유와 나란히 보인다. 둘이 다르면 다르다고 표시한다 | — |

- 한 번에 다루는 문장은 파이프라인과 같이 최대 12개(`risk.PER_TERM`)다.
- 커뮤니티 글은 쓰지 않는다. 키가 필요 없는 뉴스만 쓰므로 운영에 수집 키를 둘 필요가 없다(Plan 05의 결정 유지).

### 2. 지키는 원칙

- **자동 실행 없음.** Scheduler·Job을 두지 않는다. 사람이 누를 때만 돈다.
- **공개 사전에 쓰지 않음.** 결과는 응답으로만 돌려주고, 실행 기록 표에는 시각·용어 ID·문장 수·걸린 시간·결과 수준만 남긴다. 문장·모델 출력 원문은 저장하지 않고 로그에도 남기지 않는다.
- **파이프라인과 같은 조건.** 모델 태그와 digest, 프롬프트 해시를 수집 서버와 맞춘다. [Kaggle 실험 노트북](../../models/kaggle/gemma_risk_labeling.ipynb)과 같은 방식으로 확인한다.
- **실패해도 서비스는 정상.** Gemma가 늦거나 실패하면 수집 서버 배치 결과만 보여 주고 "지금은 다시 분류할 수 없음"이라고 알린다.

### 3. 누가 누를 수 있나 — 팀이 고를 것

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 관리자만 | `/admin/risk`에 버튼. 검수자 계정만 | 남용이 없다 | 심사위원이 직접 볼 수 없다. 영상에서만 보인다 |
| **B. 누구나, 한도 안에서 (권장)** | 사전 항목 화면에 버튼. 전체 하루 N회, 같은 용어는 10분에 한 번(결과 캐시) | 심사위원이 배포본에서 직접 누른다 | 한도에 걸리면 그날은 못 누른다 |

B를 고르면 남용 비용은 하루 한도가 막는다. 한도에 걸린 뒤에는 버튼 대신 "오늘 실행 한도를 모두 썼습니다"를 보인다.

### 4. 비용과 상한 (추정)

단가는 [Gemma 로컬 편집 결정](Gemma-로컬-편집-엔진-결정.md)의 계산을 쓴다. L4 1개 + CPU 4 + 메모리 16 GiB, **시간당 $1.05 (Tier 1 공개 단가, 하한)**.
계획 리전인 싱가포르는 Tier 2라 이보다 비싸다. 무료 사용량·세금·환율은 뺐다. 아래는 실측이 아니다.

- 한 번 누르면 켜지는 데 1~3분(종전 Plan 06의 예상치, 미실측), 처리 수십 초, 마지막 요청 뒤 최대 10분 유지된다([Cloud Run 자동 확장](https://docs.cloud.google.com/run/docs/about-instance-autoscaling)). **한 번에 약 15분 ≈ $0.26**으로 잡는다.
- 이어서 누르면 켜진 인스턴스가 받으므로 실제로는 이보다 적을 수 있다.

| 하루 한도 | 최악의 GPU 시간/일 | 하루 | 30일 |
| --- | --- | --- | --- |
| 10회 | 2.5시간 | 약 $2.6 | 약 $79 |
| 20회 | 5시간 | 약 $5.2 | 약 $157 |
| 30회 | 7.5시간 | 약 $7.8 | 약 $235 |

**가장 큰 위험: 지출 한도가 서비스 전체를 멈춘다.** 이 프로젝트의 Cloud Run 월 지출 한도(₩100,000)는 웹·API·알림 중계기를 포함한
Cloud Run 사용 전체에 걸리고, 100%에 닿으면 새 사용이 멈춰 요청이 `5xx`가 된다([GCP 운영](../운영/GCP-운영.md#예산과-리전)).
GPU 비용도 Cloud Run에 청구되므로, **버튼이 많이 눌리면 심사 기간에 웹까지 멈출 수 있다.** 그래서 다음 중 하나가 필요하다.

1. **Gemma 서비스를 별도 GCP 프로젝트에 두고 그 프로젝트에 따로 지출 한도를 건다(권장).** 한도에 닿아도 Gemma만 멈추고 웹·API는 산다.
2. 같은 프로젝트에 두려면 하루 한도를 월 지출 한도의 절반 이하가 되게 잡는다(위 표에서 10회 이하). GPU 켜짐 경보(종전 Plan 06)도 되살린다.

### 5. 기다림과 실패 처리

- 버튼을 누르면 진행 단계(준비 중 → 기사 모으는 중 → 분류 중 → 판정)와 경과 시간을 보인다. 그만두기 버튼을 둔다.
- 제한 시간(예: 4분)을 넘기면 배치 결과만 보이고 "Gemma가 아직 준비되지 않았습니다"라고 알린다.
- 기사에서 표제어가 든 문장이 5개 미만이면 모델을 부르지 않고 "지금 모을 수 있는 문장이 부족합니다"라고 알린다. 모델 비용을 아끼고 판단 보류와 같은 기준을 지킨다.

### 6. 모델과 실행 방식

| 항목 | 제안 | 이유 |
| --- | --- | --- |
| 모델 | **`gemma4:12b`** | 파이프라인·평가와 같은 모델이어야 "같은 모델, 같은 규칙"이 성립한다 |
| 실행기 | **Ollama** (수집 서버와 같은 버전) | 같은 실행기·같은 모델 파일이어야 결과를 비교할 수 있다. vLLM이 더 빠를 수 있지만 수집 서버와 조건이 달라진다 |
| 리전 | asia-southeast1(싱가포르) | 도쿄에는 Cloud Run GPU가 없다(종전 Plan 06 조사) |
| 인스턴스 | 최소 0 · 최대 1 | 평소 비용 0, 동시에 여럿이 눌러도 GPU는 하나 |
| 공개 범위 | 비공개. API 런타임 계정만 호출 | 외부에서 GPU를 직접 부를 수 없게 |
| 가중치 | 이미지에 포함 | 켜질 때 인터넷에서 받지 않게(종전 Plan 06 결정) |

종전 Plan 06은 `gemma-4-E2B-it`(Gemma 4의 가장 작은 모델, 모바일·기기용)을 골랐다. 이 제안은 파이프라인과 같은 12B를 쓴다. 12B는
L4(24 GB)에 들어가는 것으로 보지만(수집 서버 기록상 Ollama가 약 7.6 GB를 씀), 켜지는 시간과 처리 시간은 E2B보다 길 것이다. 7절에서 잰다.

### 7. 채택 전에 잴 것

[Gemma 로컬 편집 결정](Gemma-로컬-편집-엔진-결정.md)의 재검토 조건에 맞춰, 배포 전에 다음을 시험 배포로 한 번 잰다.

| 항목 | 합격선(제안) |
| --- | --- |
| 켜지는 시간 (0 → 첫 응답) | 3분 이하 |
| 한 용어 처리 시간 (켜진 상태) | 30초 이하 |
| 수집 서버 배치와의 문장 분류 일치율 | 같은 문장에서 90% 이상 (모델·실행기가 같으므로 크게 다르면 조건이 어긋난 것) |
| 한 번 누를 때 실제 청구 | Billing에서 확인해 4절 추정과 비교 |
| 지출 한도 분리 | 한도에 닿았을 때 웹·API가 계속 응답하는지 확인 |

### 8. 구현 범위 (담당은 팀이 정함)

| 영역 | 할 일 |
| --- | --- |
| 인프라 | Cloud Run GPU 서비스(비공개), 이미지 빌드, 별도 프로젝트 또는 지출 한도 조정, GPU 켜짐 경보 |
| API | `POST /terms/{term_id}/live-risk`: 권한·하루 한도·용어별 캐시, 뉴스 조회 → 분류 → 규칙 판정, 실행 기록 표(번호 붙은 마이그레이션) |
| 웹 | 사전 항목의 버튼, 진행 표시, 배치 결과와 나란히 보이는 결과, 한도·실패 안내 |
| 연구 | 7절 측정, 배치와의 일치율, 데모 영상 장면 |

### 9. 하지 않는 것

- 정기 수집·분류, 파이프라인 전체 실행
- 버튼 결과를 공개 사전·대시보드에 반영하는 것 (반영은 지금처럼 수집 서버 배치 → 검수 → 게시로만)
- 이용자가 입력한 문장을 Gemma로 분류하는 것 (사용자 입력 보존 규칙이 늘어난다)
- 최소 인스턴스를 1로 두어 늘 켜 두는 것 (월 약 $750, 결정 문서 계산)
- 운영에 YouTube·Naver 등 수집 키를 두는 것
