# Gemma 4 로컬 편집 엔진 결정과 비용 비교

결정일 **2026-09-28** · 상태 **아키텍처 결정, 운영 구현 전** · 관련 [Plan 05](../plans/05-trend-cloud-run-deployment.md) · [Plan 06](../plans/06-gemma-on-cloud-run-gpu.md)

> **2026-09-29 변경:** 아래는 9월 28일 결정의 기록이다. 최신 실행 계획은 [Plan 06](../plans/06-gemma-on-cloud-run-gpu.md)을 따른다. Gemma 실험·편집은 Colab GPU 중심으로 옮기고 소유자 Drive의 공유 폴더에 입력·결과를 보관한다. PC는 수집과 GPU 미배정 시 대체 추론 경로로 유지한다. 공개 서비스와 배치를 분리하고 승인 결과만 게시하는 원칙은 유지한다.

## 결론

- Trend Interpreter는 웹 SaaS다. 사용자의 기기에 모델 설치를 요구하지 않는다.
- 개발자 PC의 Gemma 4는 공개 트렌드 자료를 분류하고, 검증된 사전의 언어별 풀이와 국가별 해석을 **미리 만드는 편집 엔진**으로 쓴다. 결과는 검증·검수 후 Cloud SQL PostgreSQL에 게시한다.
- 웹·API는 Cloud Run, 데이터는 Cloud SQL에 둔다. 전체 수집·해석 파이프라인을 Cloud Run Job과 Scheduler로 옮기는 종전 Plan 05 결정과, Gemma 전용 Cloud Run GPU·vLLM을 배포하는 종전 Plan 06 결정은 철회한다. 운영에 Gemma 서비스를 다시 둘지는 [Plan 14](../plans/14-gemma-visible-in-deployment.md)에서 협의 중이다(미정).
- 사용자 요청 시 새로운 사진·문구를 이해하거나 카피를 생성해야 하는 부분은 Vertex AI Gemini를 사용한다. 사전 조회, 생애주기·리스크 판정, 금칙·근거 대조는 저장된 데이터와 규칙 코드가 담당한다.
- 개발자 PC가 멈추면 새 자료의 갱신은 늦어지지만, 게시된 자료의 열람과 실시간 SaaS 기능은 계속 가능해야 한다. 사용자 입력 보존 기간 정리와 운영 건강 점검은 PC 가동 여부와 분리한다.

## 왜 Gemma인가

[대회 요건](https://aibuildercup.com/themes.html)은 Google AI 모델(Gemini **또는** Gemma 등)의 활용을 허용한다. Gemma나 로컬 LLM을 반드시 써야 한다는 규정은 없다. 심사는 모델 수보다 생성형 AI가 문제를 푸는 방식, 구현, 확장성, 차별성, 사용자 경험을 본다. 따라서 Gemma의 명분은 'GPU 서비스를 하나 더 만들었다'가 아니라 **작은 오픈 모델을 증거 기반의 다국어 편집 공정에 배치해, 한 번 만든 결과를 많은 사용자에게 제공한다**는 데 있다.

[Gemma 4 모델 개요](https://ai.google.dev/gemma/docs/core)는 공개 가중치와 상용 활용·조정 가능성을 설명한다. [모델 카드](https://ai.google.dev/gemma/docs/core/model_card_4)는 요약·다국어·도구 호출 등을 가능한 용도로 들면서도 최신 사실, 풍자와 미묘한 뉘앙스의 오류 가능성을 명시한다. 트렌드의 사실 여부·검증 상태를 Gemma 혼자 판정하지 않고 근거와 규칙 게이트를 쓰는 이유다. [시작 안내](https://ai.google.dev/gemma/docs/get_started)는 E2B를 모바일, 12B를 PC·소형 서버용으로 구분한다. 현재 코드의 기본 `GEMMA_LOCAL_MODEL=gemma4:12b`와 과거 GPU 계획의 `google/gemma-4-E2B-it`는 서로 다른 모델이다. 모델별 품질·속도 실측을 공유한 것처럼 쓰지 않는다.

Cloud Run GPU + vLLM의 기술적 이점도 있다. [Google Cloud 가이드](https://docs.cloud.google.com/run/docs/run-gemma-on-cloud-run)는 vLLM의 연속 배치 처리·효율적 GPU 메모리 관리·OpenAI 호환 API를 설명한다. 자체 모델 버전과 추론 설정을 통제하고, 요청이 없는 기간에는 인스턴스를 0개로 줄일 수 있다. 하지만 현재 예상 사용량에서 처리량 이점은 실측되지 않았고, 실시간 화면에는 콜드 스타트와 GPU 가동비가 붙는다. 무엇보다 **클라우드 GPU의 모델은 사용자 기기에서 실행되는 모델이 아니다.** 기기 내 오프라인 처리나 원문이 기기 밖으로 나가지 않는다는 가치를 이 구조의 장점으로 주장하지 않는다.

### 심사에서 보여 줄 사용자 가치

| 실제 사용 장면 | 로컬 Gemma가 미리 만드는 것 | SaaS가 보여 주는 것 |
| --- | --- | --- |
| 한국에서 뜬 밈이 일본·동남아로 전해질 때 | 검증된 근거에 묶인 언어별 뜻·뉘앙스와 국가별 차이 초안 | 지역별 해석, 출처, 관측·갱신 시점 |
| 마케터가 브랜드 문구에 밈을 넣으려 할 때 | 표현의 쉬운 풀이와 사용 맥락, 근거 문장 분류 초안 | 생애주기·리스크 규칙 판정과 검수된 사전 |
| 새 자료가 들어와 뜻이 달라질 때 | 기존 뜻과 새 근거를 비교할 후보 초안 | 검수 후 새 뜻 버전과 이전 버전 이력 |

시연은 같은 항목의 **원자료 → Gemma 초안 → 근거 대조·검수 → 게시된 나라별 카드**를 이어 보여 준다. 번역의 자연스러움, 원어 표제어 보존, 출처에 없는 사실 추가, 국가별 차이의 정확도를 평가표로 제시한다. 실제로 측정하기 전에는 Gemini보다 품질이 높거나 비용이 낮다고 주장하지 않는다. 이것은 현재 기능과 목표를 바탕으로 한 시연 설계이며, 평가 결과는 아직 없다.

## 실행 경계

```text
개발자 PC: 공개 자료 수집 → Gemini가 필요한 영상·검색 조사 → 로컬 Gemma 텍스트 분류·번역·국가별 초안
                         → 코드 검증·사람 검수 → 버전·출처·실행 기록과 함께 Cloud SQL 게시
클라우드:   Cloud Run 웹·API ↔ Cloud SQL의 게시된 데이터
           사용자 사진·문구 이해 및 신규 카피 생성 → Vertex AI Gemini
           사용자 요청의 사전 조회·리스크 판정 → 저장 데이터와 규칙 코드
```

현재 `pipeline/gemini.py`는 `USE_LOCAL_GEMMA=1`일 때 텍스트 전용 호출을 로컬 모델로 보내고, 영상 입력과 Google Search grounding은 Gemini 경로로 남긴다. `pipeline/translate.py`는 검증된 현행 뜻만 번역하고 사용 모델을 DB에 기록한다. `verification.py`의 검증 게이트와 뜻 버전 이력은 그대로 유지한다. 개발 기본 스택은 `MODEL_PROVIDER=mock`, `MODEL_REQUESTS_ENABLED=false`라 유료 모델을 호출하지 않는다.

전체 파이프라인은 현행 `scripts/run_pipeline.py`를 **개발자 PC에서** 실행하는 방향이다. 운영 Cloud SQL에 게시하기 전, 현재 로컬 실행이 운영 DB와 안전하게 연결되는지, 실패한 배치가 공개 데이터를 오염시키지 않는지, 재실행 시 중복이 없는지는 별도로 구현·검증해야 한다. 원자료·초안과 공개 승인 자료의 구분, 게시 시점·모델 ID·근거·검수자 기록도 확인 대상이다. Cloud SQL 접속은 [Cloud SQL Auth Proxy 안내](https://docs.cloud.google.com/sql/docs/postgres/connect-auth-proxy)를 참고하되, 운영 DB의 공개 IP 또는 광범위한 쓰기 권한을 편의상 열지 않는다. Proxy는 인증·암호화를 제공하지만 private IP에 대한 네트워크 경로를 새로 만들지는 않는다.

이 설계에서 RAG의 검색은 게시된 뜻과 근거를 조회해 모델에 제한된 문맥으로 주는 것이다. 모델 가중치에 최신 유행어 사실이 이미 들어 있다고 가정하지 않는다. 현 사전 규모에서는 기존 PostgreSQL 검색·도구 호출을 활용하며, 벡터 DB를 새로 도입하는 결정은 아니다. [이전 로컬 파이프라인 실측](../트렌드/파이프라인.md)은 텍스트 분류·번역·재작성 가능성을 보여 주지만, 모델·GPU 점유율·환경이 바뀌면 다시 측정해야 한다.

로컬 PC의 가동이 보장되지 않으므로 화면은 마지막 성공 갱신 시각을 보여 주고, 오래된 데이터는 운영 상태로 알린다. `collect.retention` 안에 있는 사용자 입력 삭제(해석 캐시 7일·미해결 질문 30일)는 로컬 파이프라인에서 분리해 클라우드에서 정기 실행해야 한다. 구현 전에는 운영 배포 완료로 보지 않는다. 로컬 PC에 새로 들어오는 사용자 원문을 전송하지 않는다.

`/explain`의 신규 문장 재작성, `/ask`의 실시간 도구 호출, Plan 07·08의 사진 추천 이유·생성 결과 검사는 미리 만들어 둔 사전만으로 전부 해결되지 않는다. 운영에서는 저장 데이터·규칙으로 가능한 부분을 먼저 처리하고, 자유 서술이 꼭 필요한 요청은 Gemini 경로로 구현·평가한다. 이것은 **새 구현 과제**이며 현재 동작을 보장하는 설명이 아니다. 클라우드 런타임에 `USE_LOCAL_GEMMA=1`만 설정하면 개발자 PC의 Ollama에 닿는 것은 아니다.

## 비용 비교: 2026-09-28 기준 공개 정가를 사용한 예시

### 가정과 식

- 비교 대상 GPU: 종전 Plan 06의 L4 1개, CPU 4개, 메모리 16 GiB, 비영역 중복 Cloud Run 서비스. [Cloud Run 요금표](https://cloud.google.com/run/pricing)의 기본 표시 단가(L4 $0.0001867/초, CPU $0.000018/vCPU·초, 메모리 $0.000002/GiB·초)를 사용한다. 이 표의 기본 선택은 Tier 1이며 계획 리전 싱가포르는 Tier 2다. 따라서 아래 GPU 금액은 **싱가포르 견적이 아닌 비교용 하한**이다.
- GPU 인스턴스 시간당 계산: `(0.0001867 + 4 × 0.000018 + 16 × 0.000002) × 3600 = $1.04652`. GPU 부분은 $0.67212/시간이다. CPU·메모리 무료 사용량, 할인, 이미지 저장·전송·빌드, 세금·환율은 표에서 제외한다. 무료 CPU·메모리 할당량은 청구 계정의 다른 Cloud Run 사용량과 공유한다.
- Gemini: Vertex AI 글로벌 표준 `gemini-3.8-flash`의 2026-12-31까지 [입력 $0.75/100만 토큰·출력 $3.75/100만 토큰](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing). 요청당 **입력 1,000·출력 200토큰**을 가정하면 `$0.0015/회`. 출력에 포함되는 thinking 토큰, 지역별 요금, grounding, 캐싱·배치 할인, 무료 제공량은 제외한다. 2027-01-01부터 공시 표준 단가는 입력 $1.50·출력 $7.50이다.
- 코드의 폴백 `gemini-3.5-flash`는 같은 공식 표의 글로벌 표준 단가가 입력 $1.50·출력 $9.00/100만 토큰이다. 같은 1,000/200 토큰이면 **$0.0033/회**다. 폴백 비중이 커지면 Gemini 총비용도 커진다.

| 사용량 예시 | Cloud Run GPU 기준 하한 | Gemini 3.8 Flash 예시 |
| --- | ---: | ---: |
| GPU 1시간 / Gemini 약 698회 | $1.05 | $1.05 |
| GPU 42시간 / Gemini 1,000회 | $43.95 | $1.50 |
| GPU 720시간(24시간 × 30일) / Gemini 10,000회 | $753.49 | $15.00 |
| Gemini 100,000회 | GPU 가동 시간·실제 처리량에 따라 달라짐 | $150.00 |

42시간의 GPU 부분만 보면 $28.23이다. 종전 Plan 06의 '2주간 하루 3시간 ≈ $28'은 CPU·메모리를 빠뜨린 계산이다. 해당 계정에 CPU·메모리 무료 할당량이 전부 남아 있다고 가정해도, 42시간의 Tier 1 계산은 약 **$38.73**이다. 싱가포르 실청구액, 한국 원화, 기존 Cloud Run 사용량은 Billing에서 다시 확인해야 한다.

시간당 698회는 위 토큰 크기의 **가격상 교차점**일 뿐이다. E2B가 그 요청량을 시간당 처리할 수 있는지, 응답 품질이 같은지 검증한 수치가 아니다. 최소 인스턴스 0이면 유휴 시 0으로 내려갈 수 있으나 [Cloud Run 자동 확장 안내](https://docs.cloud.google.com/run/docs/about-instance-autoscaling)에 따르면 GPU 인스턴스는 마지막 요청 후 최대 10분 유지될 수 있다. 최소 1로 고정하거나 요청이 이어지면 상시 가동에 가까워진다. 720시간은 한 달 내내 **인스턴스 1개가 켜진 경우**이며 현 계획의 실제 청구 예상액이 아니다.

개발자 PC의 Gemma에는 별도 Cloud Run GPU 요금이 없다. 다만 PC 전력·장비·운영 시간은 0원이 아니고, Cloud SQL·웹·API·필요한 Gemini 호출은 계속 과금된다. 로컬 Gemma의 토큰당 비용과 경제성은 실제 배치 실행 시간·전력·인건비를 재지 않았으므로 단정하지 않는다.

종전 GPU 계획처럼 모델 가중치 약 5GiB를 Artifact Registry 이미지에 넣는다면 [저장 요금](https://cloud.google.com/artifact-registry/pricing)도 든다. 0.5GiB 무료량이 해당 청구 계정에 전부 남아 있다는 단순 가정에서 `(5 - 0.5) × 약 $0.10/GiB·월 ≈ $0.45/월`이며, 다른 이미지와 여러 버전이 있으면 늘어난다. 이 금액은 위 GPU 시간 표에 넣지 않았다.

## 채택 조건과 다음 검증

1. 검증된 용어·국가별 카드의 대표 사례를 정하고, Gemma 초안과 게시본의 변경 내역·근거 일치율·누락·재작업률을 측정한다. 모델 ID와 실행 시간도 기록하되 사용자 원문·출력 전문을 운영 로그에 남기지 않는다.
2. PC가 꺼진 상태에서 SaaS의 읽기·추천·생성이 어떻게 동작하는지, 오래된 자료가 어떻게 표시되는지 확인한다.
3. 별도 보존 기간 정리와 건강 점검이 PC 없이 실행되는지 확인한다.
4. 클라우드 GPU는 실시간 Gemma 호출이 사용자 가치나 검증 가능한 비용 이점을 제공하고, 품질·지연·처리량을 실측한 뒤에만 다시 검토한다. 지금은 배포 대상이 아니다.
