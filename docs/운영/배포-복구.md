# 배포 기록과 복구 절차

[GCP 운영](GCP-운영.md) · [개발 명령어](../개발환경/개발-명령어.md) · [현재 계획](../plans/README.md)

메인 서비스는 `builder-cup`, Discord 알림 중계기는 `builder-cup-alert-relay`입니다. 배포는
`release/gcp`에서만 시작합니다. `Release GCP`의 배포 job 요약에는 commit SHA, 이전·신규 revision,
image digest, secret **버전 번호**, 모델, 통과한 검사가 기록됩니다. Secret 값과 사용자 입력은 기록하지
않습니다. 검사가 실패하면 성공 요약이 생성되지 않고 job이 실패로 표시됩니다.

## 변경 파일 없이 서비스 재배포

서비스를 다시 만들거나 기존과 같은 소스를 새 revision으로 배포할 때, 저장소 루트의 깨끗한
`develop`에서 다음과 같이 실행합니다.

```bash
git switch develop
git fetch origin
git merge-base --is-ancestor origin/release/gcp develop
git commit --allow-empty -m "ops: 메인 서비스 재배포"
git push origin develop
git push origin develop:release/gcp
```

알림 중계기만 다시 배포할 때는 commit 제목을 `ops: 알림 중계기 재배포`로, 둘 다 필요할 때는
`ops: 전체 서비스 재배포`로 바꿉니다. 정확히 이 세 제목만 명시적 재배포 대상으로 분류합니다.
Workflow는 공통 CI를 한 번 실행한 뒤 선택한 서비스의 image를 다시 빌드해 배포합니다. 메인 서비스가
삭제된 상태라도 Artifact Registry와 IAM·secret이 남아 있으면 이 경로로 다시 만들 수 있습니다.
`git merge-base`가 실패하거나 push가 거부되면 강제 push하지 말고 브랜치 차이를 확인합니다.

## 이전 revision으로 되돌리기

1. GitHub Actions의 최근 성공 배포 요약에서 대상 서비스의 이전 revision과 image digest를 확인합니다.
2. 대상 revision의 secret 버전이 현재도 활성인지 확인합니다. 노출·폐기된 secret을 다시 활성화해
   rollback하지 않습니다.
3. 읽기 전용 점검을 먼저 실행합니다.

   ```bash
   bash scripts/rollback-gcp.sh builder-cup KNOWN_GOOD_REVISION --check
   bash scripts/rollback-gcp.sh builder-cup-alert-relay KNOWN_GOOD_RELAY_REVISION --check
   ```

4. 서비스·Ready·image digest·숫자 secret 버전 확인이 통과하면 해당 서비스에만 `--apply`를 실행합니다.

   ```bash
   bash scripts/rollback-gcp.sh builder-cup KNOWN_GOOD_REVISION --apply
   bash scripts/rollback-gcp.sh builder-cup-alert-relay KNOWN_GOOD_RELAY_REVISION --apply
   ```

`--check`는 트래픽을 변경하지 않습니다. 대상이 현재 100% 서비스 중이면 메인은 health 200과 인증 없는
분석 요청의 401을 확인하고, relay는 비공개 IAM과 인증된 health 200을 확인합니다. 이전 revision은
traffic을 받지 않으므로 메타데이터와 secret 상태까지 먼저 확인합니다. `--apply`는 대상을 100%로
전환한 뒤 같은 HTTP 검사를 실행합니다. 사후 검사가 실패하면 이전 100% revision으로 traffic을
돌리고 오류로 종료합니다. 전환 중 처리 중이던 요청은 계속 완료될 수 있습니다.

**메인 서비스의 과거 `latest` 참조 revision은 이 안전 복구 명령에서 거부합니다.** 숫자 secret 버전을
사용하는 새 revision부터 설정까지 재현 가능합니다. Secret 값이 노출됐거나 version을 폐기했다면 이전
revision으로 돌아가지 말고 새 secret version과 새 revision을 배포합니다.

## 배포가 실패했을 때

- 후보 revision의 health 또는 익명 접근 검사 실패 시 기존 100% traffic은 유지됩니다. 원인을 수정하고
  새 release를 실행합니다.
- 배포 job은 성공했는데 사용 중 문제가 생겼다면 위의 `--check`로 이전 revision을 확인한 뒤
  `--apply`로 되돌립니다. 이어 `develop`의 문제 commit을 수정하거나 revert하고 release에 반영합니다.
- relay 복구에서는 public invoker를 열지 않습니다. 현재 gcloud 사용자는 Cloud Run 호출 권한으로
  인증 health를 확인하며, GitHub 배포 job은 audience가 지정된 service account ID token을 사용합니다.
- 실제 운영 traffic을 이전 revision으로 옮기는 연습은 평가·사용 중인 시간에 자동 실행하지 않습니다.

CI 성공은 저장소 공통 stack의 검사 결과입니다. `prototype/` 후보 전체의 품질이나 실제 Gemini 접근을
입증하지 않습니다. 새 팀원의 Mac 재현 여부는 [개발환경 완료 기록](../plans/archive/01-environment-reproducibility.md)의
남은 확인 항목을 따릅니다.
