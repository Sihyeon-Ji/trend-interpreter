## 검토한 방법과 결론

| 안 | 내용 | 결론 |
| --- | --- | --- |
| **A. 검사 이미지 캐시** | `check`·`e2e` 빌드에 GitHub Actions 캐시(`type=gha`)를 쓴다 | **하지 않는다.** 시험 결과 효과가 없고 캐시 한도도 부담이다(아래) |
| **B. develop에서 미리 검사하고 결과 재사용** | `develop` push에도 CI를 돌리고, 같은 커밋이면 release의 검사를 건너뛴다 | **하지 않는다.** GitHub Actions 무료 등급은 월 실행 시간(비공개 저장소 2,000분)에 한도가 있어 `develop` push마다 CI를 돌리기 어렵다. 효과도 `trend_images`가 남아 4분 안팎에 그친다 |
| **C. API·웹 동시 배포** | `deploy-trend.sh`에서 두 서비스를 동시에 배포한다 | **하지 않는다.** 순서는 의도다. 웹 후보는 새 API로 트래픽을 옮긴 뒤 그 API를 거쳐 첫 화면·브리핑을 열어 확인한다(`deploy-trend.sh` 머리말). 웹 후보 배포만 앞당겨도 20초 안팎이라 확인 순서를 흔들 만하지 않다 |
| **D. runner 대기** | 대기는 GitHub 쪽 사정이다 | 손댈 곳 없음 |
| **E. `Dockerfile.dev` 층 순서** | 의존성 파일만 먼저 복사해 설치하고, 소스는 그 뒤에 복사한다 | **적용(10-06).** 로컬에서 API 코드를 고친 뒤 검사 이미지 재빌드가 약 30초로 줄었다(의존성 층 재사용). CI는 실행마다 새 runner라 층 캐시가 없어 CI 시간은 그대로다 |

### A 시험 결과(10-06)

시험 브랜치에서 `CI`를 두 번 수동 실행했다(37399381149·37400012411). 브랜치와 시험용 캐시 목록은 시험 뒤 지웠다.

| job | 지금(배포 실행) | 첫 실행(캐시 채움) | 둘째 실행(캐시 사용) |
| --- | --- | --- | --- |
| app | 4분 10초 | 6분 55초 | 4분 8초 |
| e2e | 3분 40초 | 6분 55초 | 2분 20초에 runner 종료 신호로 중단 |

- 캐시는 맞았지만, buildx가 만든 이미지를 docker로 옮기는(`load`) 데 app 이미지에서 약 70초가 들어 줄인 시간을 거의 다 썼다. 검사 이미지에 Python 환경 셋과 Node 패키지가 모두 들어 있어 크다.
- e2e는 세 번째 이미지(브라우저 시험용)를 옮기던 중 runner가 멈췄다. 큰 이미지를 두 벌씩 들고 있어 자원이 모자랐을 가능성이 있으나 확인하지 않았다.
- 시험용 캐시만으로 약 1GB가 쌓였다. 저장소 캐시 한도(10GB)를 넘으면 배포용 이미지 캐시가 밀려나 `trend_images`가 오히려 느려질 수 있다.

## force push 뒤 전체 범위

`scripts/release_scope.py`는 직전 `release/gcp` 커밋과 새 커밋의 차이로 범위를 정한다. 10-06에 커밋 메시지를 고치려고 force push했을 때는 직전 커밋(`e345202`)이 어느 브랜치에도 남지 않아 runner가 받아 오지 못했다. 이때 차이를 구할 수 없으니 전체(`full`·`infra`·`app`·`relay`)로 잡는다. 코드상 그렇게 동작하며, 실행 37395937157에서 인프라 검사와 알림 중계기 배포가 돈 것과 맞다. 안전한 쪽으로 넓게 잡는 것이라 고칠 대상은 아니다.
