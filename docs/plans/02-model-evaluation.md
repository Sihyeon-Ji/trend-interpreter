# 02. 모델 평가와 비교 보고서

상태 **계획 작성 완료·구현 미착수** · 우선순위 **먼저** · [전체 계획](README.md)

## 해결할 문제와 목표

5단계에서 JSON 형식은 통과했지만 시간 누락과 의미 왜곡을 발견했습니다.
현재 합성 사례 3개와 원문·결과 보고서만으로는 프롬프트나 모델을 바꿨을 때 무엇이 좋아지거나 나빠졌는지
일관되게 판단하기 어렵습니다.

목표는 **실험 조건과 평가 기준을 고정하고, 두 실행에서 달라진 내용·지연·사용량을 비교하는 절차**를 만드는 것입니다.
최종 주제의 정답 데이터나 제품 합격 점수를 미리 확정하지 않습니다.

## 구현 범위

- 기존 합성 사례를 유지하고 주제 중립적인 사례를 총 10개 정도로 확장합니다.
- 날짜·시간, 담당자와 업무 관계, 변경 전후 값, 부정·미정 정보, 입력 내부 지시문을 각각 다룹니다.
- 사례마다 보존할 사실·금지 주장·입력 근거를 명시합니다.
- 형식 검사와 내용 평가를 분리합니다. 문자열 일치만으로 의미 정확성을 확정하지 않습니다.
- 보고서에 사례 버전 또는 해시, 코드 커밋, 모델 digest, 프롬프트 버전, 추론 설정, 실행 ID를 연결합니다.
- 이전 보고서와 새 보고서의 변경·누락·시간·토큰 차이를 요약합니다.

실험 중 변경 변수는 한 번에 하나로 제한합니다. 초기 비교는 현재 모델과 설정을 유지한 채
평가 체계를 검증하고, 이후 프롬프트 변경과 모델 변경을 각각 별도 실행으로 비교합니다.

## 진행 순서

1. 기존 보고서에서 확인한 시간 누락·업무 관계 왜곡을 회귀 사례로 정리합니다.
2. 사례와 평가 기록의 최소 구조를 정의합니다. 사실별 결과는 충족·누락·모순·근거 없는 추가·검토 필요로 구분합니다.
3. 결정적으로 검사할 수 있는 출력 형식·필수 필드와 원문 대조가 필요한 의미 평가를 구분합니다.
4. 같은 조건의 기준 실행을 남기고, 의도적으로 누락된 응답으로 보고서가 문제를 표시하는지 확인합니다.
5. 두 보고서를 비교하는 기능과 평가자·검토일·근거를 남기는 절차를 추가합니다.

## 완료 기준과 확인 방법

| 기준 | 확인 방법 |
| --- | --- |
| 형식 성공과 내용 성공 구분 | 올바른 JSON이지만 시간이 빠진 응답을 별도 품질 문제로 표시 |
| 실행 조건 재현 가능 | 모델·프롬프트·사례·설정·코드 버전이 보고서에서 식별됨 |
| 변경 효과 비교 가능 | 같은 사례 ID끼리 비교하고 사례가 바뀐 경우 직접 비교 불가로 표시 |
| 평가 근거 추적 가능 | 내용 판정마다 원문 근거와 출력의 해당 표현, 평가 주체를 기록 |
| 비용과 성능을 과장하지 않음 | 미보고 토큰은 미확인, 초기 로딩과 후속 요청 시간을 분리 |
| CI가 실제 모델에 의존하지 않음 | 보고서 비교·파싱은 고정 fixture로 검사, 실제 추론은 명시적 로컬 실행 |

초기에는 기준 사례의 원문 대조와 평가 주체를 명시한 검토 기록을 사용합니다.
자동 점수가 추가되더라도 의미 정확도의 완전한 판정으로 표현하지 않습니다.
현재 3개 사례에서 품질이 좋았다는 사실을 전체 정확도 비율로 확대하지 않습니다.

## 산출물과 제외 범위

산출물은 합성 평가 사례, 평가 기준, 비교 보고서 형식과 생성 코드, 재현 가능한 비교 예시입니다.
원문·생성 결과를 포함한 실행 산출물은 계속 `artifacts/`에 보관하고 Git에는 합성 fixture와 코드·기준만 반영합니다.
유료 LLM 평가자, 새 대형 모델 다운로드, 모델 학습·미세조정, 도메인별 합격선, 프롬프트 공격 방어 완료 주장은 포함하지 않습니다.
