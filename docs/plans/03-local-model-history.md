# 03. 실제 모델 비교와 실행 이력 연결

상태 **계획 작성 완료·구현 미착수** · 우선순위 **02 이후** · [전체 계획](README.md)

## 해결할 문제와 목표

현재 Mock 그래프는 PostgreSQL과 웹에서 이력을 볼 수 있지만, 실제 Ollama 비교는 JSON·Markdown 파일에만 남습니다.
실제 모델이 느리거나 실패했을 때 같은 실행 ID로 보고서와 단계별 이력을 연결해 보고 싶습니다.

목표는 **실제 모델 비교를 명시적으로 실행하면 기존 Workflow history에서도 메타데이터를 확인하는 것**입니다.
최종 제품 화면을 설계하거나 기본 웹 분석 모델을 바꾸는 작업은 포함하지 않습니다.

## 가장 작은 구현 방향

- 기존 `ollama-check`의 파일 비교 흐름을 유지합니다.
- DB 기록이 필요한 실습에만 opt-in Compose 명령을 제공합니다. 별도 `ollama-history-check` 서비스를 후보로 둡니다.
- 이 명령에서 기존 `history.run_with_history`를 재사용하고 보고서의 실행 ID와 DB 실행 ID를 일치시킵니다.
- 해당 명령에만 앱 DB 비밀번호 볼륨을 읽기 전용으로 연결하고 DB 초기화 완료를 기다립니다.
- 기존 웹의 목록·상세에서 Provider·모델을 명확히 표시해 Mock과 Ollama 실행을 구분합니다.
- 원문·생성 결과는 평가 파일에만 두고 DB에는 메타데이터만 저장합니다.

실제 추론의 진입점은 계속 명시적인 Compose 명령입니다. 기본 API는 Mock을 유지하고,
API의 로컬 Mock 실습 제한을 포괄적으로 풀지 않습니다. 별도 API·웹 스택이나 새 포트는 우선 추가하지 않습니다.

## 진행 순서

1. [02 계획](02-model-evaluation.md)의 보고서·사례·실행 ID 연결 방식을 확인합니다.
2. 비교 실행 함수에서 저장 여부를 명시적으로 선택하고, 이력 저장 경로를 재사용합니다.
3. 실제 모델의 오류 코드·토큰·시도 횟수·노드 상태가 기존 형식으로 저장되는지 확인합니다.
4. 파일 보고서의 ID를 웹 이력에서 조회하고 같은 실행인지 대조합니다.
5. 시작 DB 쓰기 실패와 종료 DB 쓰기 실패가 보고서·HTTP 외 실행 결과에 어떻게 나타나는지 일치시킵니다.

## 완료 기준과 확인 방법

| 기준 | 확인 방법 |
| --- | --- |
| 정상 실행 연결 | 보고서와 DB의 ID·Provider·모델·토큰·노드 상태 일치 |
| 실패 실행 연결 | 모델 접근 실패·시간 초과를 실패로 기록, Mock으로 대체하지 않음 |
| DB 장애 정책 유지 | 시작 쓰기 실패 시 모델 미호출, 종료 쓰기 실패 시 정상 저장 완료로 보고하지 않음 |
| 입력 보관 범위 유지 | DB 응답과 운영 로그에 합성 원문 표식·생성 결과가 없는지 확인 |
| 기본 흐름 유지 | Mock 웹·기존 실패 시나리오·DB 없는 `ollama-check`가 계속 동작 |
| 실제 모델 여부가 명확함 | 목록 또는 상세에서 Mock과 Ollama를 구분하고 원문은 이력으로 복원할 수 없음을 안내 |

자동 검사는 가짜 Provider와 테스트 DB로 수행하고, 실제 모델 검증은 명시적으로 한정한 합성 입력으로 진행합니다.
UI 변경이 있으면 실행 항목 선택과 오류 표시에 해당하는 브라우저 검사를 수행합니다.

## 산출물과 제외 범위

산출물은 opt-in Compose 정의, 최소 실행 코드 변경, 이력 연결 검사와 갱신한 명령어 안내입니다.
새 DB 열이 정말 필요한지는 구현 전에 확인하며 기존 실행 ID로 충분하면 스키마를 확장하지 않습니다.
실제 모델을 호출하는 일반 사용자용 웹 기능, 원문 DB 저장, 자동 재개, 실시간 토큰 스트리밍, 클라우드 모델은 포함하지 않습니다.
