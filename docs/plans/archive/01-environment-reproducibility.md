# 01. 개발환경 재현성과 진단

상태 **구현 완료·현재 Mac 검증 통과·다른 팀원 Mac 검증은 온보딩 시 확인** · [현재 계획](../README.md)

## 해결할 문제와 목표

지금까지의 기동·모델 추론은 주로 한 Mac에서 확인했습니다. 다른 팀원이 clone했을 때도 개인 경로나
기존 DB 볼륨·캐시·호스트 패키지에 기대지 않고 개발을 시작할 수 있어야 합니다.
Ollama의 ‘설치됨’, ‘서버 실행 중’, ‘모델 다운로드됨’, ‘실제 추론 성공’을 따로 설명할 필요도 있습니다.

목표는 **설치가 막히면 어느 준비가 부족한지 알 수 있고, 새 환경에서 현재 명령을 재현할 수 있게 하는 것**입니다.

## 구현 범위

- 기본 개발에 필요한 Docker 엔진·Compose·포트와 현재 서비스 상태를 점검합니다.
- 선택적 Ollama 준비 상태를 별도 항목으로 보여 줍니다. 미설치는 기본 Mock 개발의 실패로 처리하지 않습니다.
- Docker에서 Mac의 Ollama에 접근할 수 있는지 확인하되, 기본 진단으로 실제 추론을 실행하지 않습니다.
- 프로젝트 루트·현재 checkout·Compose 프로젝트 이름을 확인해 잘못된 디렉터리 실행을 구분합니다.
- Mac 설치 안내에 진단 결과별 다음 행동과 예상 정상 상태를 연결합니다.

진단은 **읽기 전용**으로 설계했습니다. `doctor`라는 opt-in Compose 서비스를 추가하되,
컨테이너가 볼 수 없는 호스트 CLI·서비스 상태는 기존 호스트 명령으로 확인합니다.
호스트 상태를 보기 위해 Docker 소켓을 진단 컨테이너에 마운트하거나 관리자 권한을 주지 않습니다.

## 진행 순서

1. [현재 설치 안내](../../개발환경/macOS-설치-진단.md)대로 필요한 조건과 실패 메시지를 목록화합니다.
2. 자동 진단 항목과 사람이 호스트에서 확인할 항목을 나눠 읽기 전용 출력을 구현합니다.
3. 별도 checkout과 고유한 Compose 프로젝트 이름으로 기존 DB와 분리해 처음부터 기동합니다.
4. 포트 충돌을 피할 검증용 설정을 준비하고 기존 서비스·볼륨이 변경되지 않았는지 확인합니다.
5. 가능할 때 팀원 Mac 한 대에서 같은 안내를 따라 실행하고 차이를 기록합니다.

## 완료 기준과 확인 방법

| 기준 | 확인 방법 |
| --- | --- |
| Ollama 없이 기본 개발 가능 | 모델 미준비 상태에서 Mock 기동·검사 성공 |
| 개인 경로에 의존하지 않음 | 다른 checkout 경로에서 DB·API·웹 및 기본 실습 실행 |
| 새 DB 초기화 가능 | 별도 빈 볼륨에서 초기화 후 기록 생성·조회 |
| 진단이 상태를 바꾸지 않음 | 실행 전후 서비스·볼륨·패키지·모델 상태 비교 |
| 설치와 실행을 구분 | Ollama 설치/서버 중지, 모델 미설치, 서버 실행 상태별 안내 확인 |
| 실제 팀원 재현성 확인 | 다른 Mac의 OS·칩·Docker 버전과 성공/실패 기록 확보 |

같은 Mac의 새 checkout 검증은 다른 Mac 검증의 대체 증거로 표시하지 않습니다.
다른 Mac을 아직 사용할 수 없다면 마지막 항목은 미검증으로 남깁니다.

## 산출물과 제외 범위

산출물은 진단 출력, 필요한 최소 스크립트·Compose 설정, 갱신한 설치 안내, 환경별 재현 기록입니다.
실제 코드를 추가하면 실패 메시지 분기와 상태 비변경을 검증하고, 기본 `check`와 해당 기동 흐름을 확인합니다.
Windows 실제 검증, 패키지 자동 업데이트, 모델 자동 다운로드, 다른 팀원의 장비 원격 변경은 포함하지 않습니다.

## 구현 결과

`docker compose run --rm --build doctor`를 추가했습니다. 이 명령은 API·웹 프록시·DB 이력 조회가
기본 Mock으로 준비됐는지 확인하고, 선택적으로 Docker에서 Ollama 서버와 `gemma4:e4b` 목록을 조회합니다.
의존 서비스를 자동 시작하지 않고 GET 요청만 사용하며 DB 비밀번호·Docker 소켓·호스트 `.env`를 받지 않습니다.
모델 다운로드와 추론도 실행하지 않습니다.

Compose의 개발 포트는 기본값을 유지하면서 `DEV_API_PORT`와 `DEV_WEB_PORT`로 바꿀 수 있게 했습니다.
`COMPOSE_PROJECT_NAME`과 함께 사용하면 다른 checkout의 컨테이너·네트워크·볼륨·포트를 분리할 수 있습니다.
`db-check`가 출력하는 브라우저 주소도 변경한 API 포트를 반영합니다.

Mac 안내와 명령어 문서에는 호스트에서 확인할 경로·브랜치·Docker context·포트·Ollama CLI와
진단 결과별 다음 행동을 추가했습니다. CI도 개발 서비스를 시작한 뒤 `doctor`를 실행합니다.

## 검증 기록 – 2026-09-22

검증 환경은 macOS 27.0, Apple Silicon, Docker Engine 29.8.0, Docker Compose 5.5.1입니다.
이 환경 하나의 결과이며 다른 팀원의 Mac이나 Intel Mac 결과로 해석하지 않습니다.

| 확인 항목 | 실제 결과 |
| --- | --- |
| 현재 개발 프로젝트 | API·웹 프록시·DB 이력 읽기·선택적 Ollama 서버/모델 모두 진단 통과 |
| 진단의 읽기 전용 범위 | `doctor` 실행 전후 원래 컨테이너 ID·시작 시각·마운트, DB 이력, Ollama 모델 목록이 동일 |
| 서비스가 꺼진 새 프로젝트 | 핵심 서비스는 `FAIL`, Ollama는 `OPTIONAL`로 구분하고 종료 코드 1, 의존 서비스 자동 기동 없음 |
| Ollama 없는 상태 | 격리 진단에서 Ollama 접근 불가여도 Mock API·웹·DB 진단 통과 |
| Ollama 상태 분기 | 서버 중지·모델 미설치·설치·잘못된 응답을 HTTP fixture 자동 테스트로 검증 |
| 별도 checkout | 공백이 포함된 `/tmp` 경로, 호스트 `.venv`·`node_modules` 없이 실행 |
| 캐시 없는 도구 이미지 | 고유 프로젝트 이름으로 `check` 이미지를 `--no-cache` 빌드 성공 |
| 포트 분리 | 기존 8000·5173과 동시에 18000·15173에서 API·웹 Mock 상태 확인 |
| 새 DB 볼륨 | 기존 볼륨 없이 초기화 후 합성 기록 생성·조회 성공 |
| 격리 컨테이너 재생성 | `down` 후 `up`에서 같은 ID·이름·생성 시각 유지 |
| 코드 검사 | Python 테스트 62개, Mock 계약 평가 2개, 타입 검사와 웹 빌드 통과 |
| 브라우저 검사 | 기존 개발 화면·이력·실패 실습 7개 통과 |

격리 DB의 검증 기록 ID는 `98900fc9-9c50-48b1-bc80-6ae9c6eb2f34`입니다.
이 ID는 `builder-cup-plan01-20260921` 프로젝트의 로컬 검증 볼륨에만 있으며 clone으로 전달되지 않습니다.
격리 검증은 기존 개발 프로젝트를 건드리지 않았습니다. 이후 최종 `e2e`가 변경된 Compose 설정을 적용하면서
기본 API·웹 컨테이너는 재생성됐고, 개발 DB 컨테이너와 데이터·비밀번호 볼륨은 유지됐습니다.

## 남은 확인

다른 팀원 Mac에서 [Mac 설치 안내](../../개발환경/macOS-설치-진단.md)를 따라 실행한 증거는 아직 없습니다.
따라서 **현재 Mac의 재현성과 진단 구현은 완료**, **팀 전체 재현성 확인은 대기**로 유지합니다.
실제 팀원 검증 시 OS·칩·Docker/Compose 버전, checkout 경로, `doctor` 출력, 기본 기동·검사 결과를
비밀정보와 개인 경로를 제외하고 이 절에 추가하면 Plan 01을 완전히 종료할 수 있습니다.

## 재점검 – 2026-09-22

구현 범위, 자동 테스트, 현재 Mac과 격리 checkout 검증을 다시 대조한 결과 **Plan 01의 구현은 완료**로 판단했습니다.
다른 팀원 Mac 검증은 구현 결함이 아니라 실제 배포 환경을 넓히는 확인 항목으로 남깁니다.
Plan 02는 기존 합성 사례와 Ollama 비교 명령만 필요하므로 이 외부 확인을 기다리지 않고 진행할 수 있습니다.
