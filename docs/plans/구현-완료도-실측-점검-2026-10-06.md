## 판정과 범위

**10-03의 '배포 기반 준비'에서 실제 운영 웹·API·DB와 예약 운영 작업이 있는 단계로 진행했다. 제출을 막는 중심 문제는 이제 데이터·AI 품질과 승인 게시 경계다.**

기준은 `develop`의 `8e348ee`와 이번 성향 분석 도구 변경이다. 현행 계획 01~17·19·20의 목표·완료 조건, archive 완료 기록, 10-03 이후 커밋과 코드·manifest를 대조했다. GCP·GitHub·Kaggle 현재 원격 상태를 새로 조회한 점검은 아니다. 운영 결과는 날짜 있는 저장소 기록으로만 확인하며, 과거 snapshot 수치를 오늘의 운영 DB 수치라고 표현하지 않는다.

계획의 크기와 조건이 다르므로 전체 구현률 백분율을 합산하지 않는다. **현행 19개 중 Plan 02만 변경된 완료 조건을 충족했다고 기록돼 있다.** 이것을 전체 작업의 1/19 진행률로 해석해서는 안 된다. 나머지에는 핵심 기능·실배포까지 끝나고 독립 평가만 남은 계획도 있다. Plan 18과 과거 운영 일정 Plan 20은 archive의 완료 계획이며, 현행 Plan 20(화면 개편)과 다르다.

## 재점검 후 바로 구현 – 공개 조회와 검수 권한 경계

사용자의 후속 요청으로 `develop`에서 공개 조회 경계를 구현했다. 위 계획별 표와 우선순위의 노출 문제는 작업 시작 때의 판정이며, 이 절이 후속 변경을 기록한다. 운영 배포는 아직 하지 않았다.

- 공개 `/terms`는 verified만 조회한다. `status=all`은 422이며 검수자용 `/review/terms`로 옮겼다. `/terms/{id}`·topic·graph·signals·generations는 용어가 verified이고 현재 뜻이 verified_auto/verified_human일 때만 열리고 나머지는 404다. 공개 뜻 이력에는 승인되지 않은 과거 판을 넣지 않는다.
- `/review/terms`·상세·queue·stats, `/pipeline/stages`, `/model-usage`, `/candidates`는 서버 전용 `FRONTEND_API_TOKEN` 없이는 401이다. 허용된 검수 조회 응답도 `Cache-Control: private, no-store`를 사용한다.
- 웹 데이터 조회 함수가 서명·만료를 검증한 세션의 reviewer 여부를 확인한다. 익명·일반 계정은 API 조회 전에 거부하며, 검수자일 때만 서버 토큰을 붙인다. Proxy의 `/admin` 차단과 별도로 데이터를 읽는 곳에서도 확인한다. 토큰은 브라우저로 보내지 않는다.
- 공개 메시지 해석과 챗봇의 정확/느슨/뜻 검색에서 검수 대기 뜻을 제외한다. 외부 위키 본문을 읽는 검색은 사전의 승인되지 않은 뜻을 읽는 경로와 구분한다.
- 사전 색인은 공개 규칙 판과 현재 뜻의 승인 상태를 해시에 넣어 이전 캐시·승인 상태 변경을 감지한다. 해석 캐시도 공개 조회용으로 분리하고 현재 매칭 항목이 달라졌으면 다시 계산한다. 웹 사전/해석 상세는 공유 캐시를 재사용하지 않아 제외된 뜻이 캐시에서 다시 나오지 않게 한다.
- 예시 모드에도 같은 공개 필터를 적용한다. `galau`의 공개 사전 화면은 없는 말 안내로 바뀌고 검수 화면의 제안은 유지한다.

API는 프론트 서버를 신뢰하는 기존 토큰 방식을 유지한다. 최종 이용자의 세션은 웹이 확인하고, Cloud Run IAM은 웹→API 서비스 인증을 별도로 맡는다. 운영의 웹/API에 같은 서버 토큰 설정이 있어야 한다. 기존 검수 쓰기에 이미 필요한 설정이며 새 secret이나 IAM 변경은 추가하지 않았다.

이 변경은 **조회 권한 경계**를 해결한 것이다. 변경 배치의 `batch_id`·`publication_id`, 멱등 게시·오래된 뜻 판 충돌·번역 초안 승인 게시(Plan 06·17)는 별도 잔여 작업이다. 웹/API는 같은 release로 배포해야 하며, 기존 `/terms?status=all` 호출자는 서버 토큰을 쓰는 `/review/terms`로 옮겨야 한다.

**후속 검증 완료:** `docker compose run --rm --build check` 종료 코드 0(데이터 20·API 404·배포/검토 24·relay 10·웹 단위 21개, lint·production build 통과). `docker compose run --rm --build e2e` 종료 코드 0, **45개 통과**. `git diff --check`도 통과했다.

새 API 회귀 검사 13개는 서버 토큰 없음/틀림/미설정, 공개 목록·상세·뜻 이력·관련 경로, 검수자 읽기, 승인/제외 전후, 색인·해석 캐시, 챗봇 검색을 확인한다. 새 웹 단위 검사 5개는 서명된 일반/검수자 세션·익명·만료/변조·토큰 누락·요청별 권한 확인·공개 뜻 필터를 확인한다. e2e는 검수 대기 사전 항목 차단과 익명/일반 계정의 관리자 접근 거부, 기존 검수자 흐름을 확인했다.

API 회귀 검사는 임시 PostgreSQL의 합성 자료, e2e는 sample/mock이다. 실제 운영 배포·원격 IAM·운영 계정 검증·유료 모델 호출·AI 품질 판정은 이번 작업 범위 밖이다.

## 남은 작업의 우선순위

Plan 01(10-01)·03(10-04)·12(10-04)은 전체 조건 기준으로 목표일을 넘겼고, Plan 16(10-06)은 수량 조건만 충족했다. Plan 02는 변경된 기준을 10-06에 충족했다. 목표일을 임의로 미루거나 과거 조건을 완료 처리하지 않고, 아래 순서로 제출 필수 경로를 먼저 마친다.

1. **공개와 검수의 경계(05·06·12·17, 재점검 시작 때).** 당시 코드에서는 `/terms?status=all`은 검수 대기 자료를 반환하고, 상세 조회는 retired만 차단하며, `explain`은 needs_review를 매칭한다. ## 이번에 바로 진행한 작업 – Plan 16 성향 분석

`apps/trend-api/scripts/meme_tendency.py`의 기본 연결을 `db.connect_read_only()`로 바꿨다. DDL·마이그레이션을 실행하지 않고 PostgreSQL 서버가 쓰기를 거부한다. `--sqlite`는 기존 고정 사본을 읽기 전용으로 열며, `--out`으로 결과 위치를 정한다. 한 보고서의 모든 SELECT는 같은 읽기 트랜잭션에서 실행한다(PostgreSQL REPEATABLE READ).

PostgreSQL에서 실패하던 `sqlite_master` 확인과 서브쿼리 별칭을 보완하고, 비중 차가 같을 때 항목 이름으로 정렬해 같은 입력의 결과를 고정했다. 빈 사본의 0 나누기도 수정했다. 조회수 최고 연도는 '조회 관심 최고 연도'로 적어 실제 유행 시기와 구분하고, 생성 Markdown에는 en dash를 쓴다.

```bash
# apps/trend-api에서, DATABASE_URL이 가리키는 PostgreSQL 읽기
uv run scripts/meme_tendency.py --out data/work/catalog

# 이전 SQLite 고정 사본 분석
uv run scripts/meme_tendency.py --sqlite data/trend.db --out data/work/catalog
```

두 DB에 같은 합성 고정 자료를 넣고 JSON 집계 일치를 확인하는 검사, PostgreSQL/SQLite 쓰기 거부, 파일 없음, 페이지뷰 표 없는 빈 사본 검사를 추가했다. 이 검증은 DB 호환성의 근거이며 실데이터 품질이나 운영 DB 분석 완료의 근거는 아니다.
