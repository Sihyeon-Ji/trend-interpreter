## 목적

팀원이 자기 Google 계정의 **Colab GPU 런타임**에서 Ollama와 Gemma 4를 실행해 공개 트렌드 근거의 리스크 분류를 실험하고, 검증된 사전 언어판·국가별 해석의 초안을 **오프라인 배치**로 만든다. 근거 대조·규칙 검증·사람 검수를 통과한 결과만 Cloud SQL에 게시한다. SaaS 사용자는 Cloud Run 웹·API에서 마지막 성공 게시본을 읽고, 사용자별 실시간 생성이 필요할 때 Vertex AI Gemini를 사용한다. **Colab이 꺼져도 공개 서비스는 동작해야 한다.**

대회는 Gemini 또는 Gemma 등 Google AI 모델의 활용을 허용한다. Gemma의 역할은 공개 트렌드 자료를 작은 오픈 모델로 가공해 여러 사용자에게 재사용 가능한 지식 자산을 만드는 것이다. 모델 이름보다 원자료·근거·검수·게시 결과를 연결해 보여 준다.

현재 `models/colab/gemma_risk_labeling.ipynb`는 **Plan 03 리스크 분류의 프롬프트·모델 비교용**이다. Gemma 가중치를 학습하거나 미세조정하지 않으며, 사전 번역·국가별 해석을 만들거나 Cloud SQL에 게시하지도 않는다. 표본 CSV와 서버 환경 JSON이 없으면 합성 문장으로 작동만 확인하므로 품질 수치로 사용하지 않는다. 이 노트북의 존재만으로 Plan 06이 구현됐다고 기록하지 않는다.

## GitHub·Colab VM·팀 Drive의 역할

| 위치 | 담는 것 | 보존·접근 |
| --- | --- | --- |
| GitHub `develop` | `.ipynb` 코드, 배치 입출력 계약, 검증 코드 | 팀이 버전 관리한다. URL에 커밋 해시가 있으면 그 버전으로 고정되므로 최신 작업은 `develop` 또는 작업 브랜치에서 연다 |
| 팀원별 Colab VM `/content` | 실행 중 설치한 Ollama, 받은 `gemma4:12b`, 입력 사본, 임시 출력 | 계정마다 별개다. GPU 배정은 보장되지 않고 런타임 종료 시 파일과 모델이 사라진다 |
| 한 소유자의 비공개 Google Drive 폴더 | 공유 표본, 환경 JSON, 실행 메타데이터, 결과·검수 파일, 미세조정 시 어댑터와 학습 재개 체크포인트 | 소유자가 특정 팀원 계정에 공유한다. 팀원은 **자기 계정**으로 Colab에 로그인하고 자기 Drive를 마운트한다 |
| 로컬 PostgreSQL·Cloud SQL | 원자료·검수 기록·마지막 승인 게시본 | Drive나 Colab을 운영 DB로 쓰지 않는다. Colab에 DB 비밀번호나 전체 DB 덤프를 올리지 않는다 |

GitHub에서 열었다고 노트북 파일이 VM의 `/content`에 복사되는 것은 아니다. Colab의 **Drive로 복사**는 개인 Drive에 편집 가능한 노트북 사본을 만든다. 코드 변경은 개인 사본 또는 작업 브랜치에서 진행하고, 출력 셀과 원문을 제거한 PR로 검토해 `develop`에 반영한다. 같은 `.ipynb`를 여러 사람이 바로 `develop`에 저장하지 않는다. CSV·모델 파일·자격증명·검수 결과는 Git에 커밋하지 않는다. [Colab FAQ](https://research.google.com/colaboratory/faq.html)는 노트북 공유와 VM 공유가 별개이고 무료 GPU·실행 시간이 보장되지 않는다고 설명한다.

## 한 사람의 Google Drive를 팀 보관소로 사용

1. 소유자 계정의 Drive에 예를 들어 `Trend-Colab/inputs`, `Trend-Colab/runs`, `Trend-Colab/checkpoints`, `Trend-Colab/approved`를 만들고 **특정 팀원 계정**에만 필요한 권한을 준다. 링크 전체 공개는 하지 않는다. 팀원별 `runs/<이름>/<실행 ID>`를 사용해 동시에 실행해도 덮어쓰지 않게 한다. 팀원이 바뀌면 권한을 정리한다. 개인 Drive의 공유 폴더이며 Google Workspace의 별도 **공유 드라이브** 상품을 전제로 하지 않는다([Drive 폴더 공유](https://support.google.com/drive/answer/7166529)).
2. 팀원은 자기 계정에서 공유 폴더를 열고 필요하면 `내 드라이브`에 바로가기를 추가한다([공유 폴더 바로가기](https://support.google.com/drive/answer/2375057)). Colab에서 **자기 Drive**를 마운트한 뒤, 실제 보이는 경로를 확인해 사용한다.

   ```python
   from google.colab import drive
   drive.mount('/content/drive')
   ```

3. 입력은 Drive에서 VM의 `/content`로 복사해 읽고, 결과는 **런타임이 살아 있을 때** Drive의 실행별 폴더로 복사한다. 지금 리스크 노트북은 `files.upload()`와 ZIP 다운로드를 사용하며 Drive 자동 입출력은 아직 없다. 이를 추가하기 전에는 매번 CSV와 `.env.json`을 업로드하고 결과 ZIP을 내려받아 Drive에 넣는다.
4. 새 VM에서는 설치 셀과 `ollama pull`을 다시 실행한다. Drive에 표본·결과가 남아도 VM의 Ollama 설치·모델 메모리·실행 상태는 남지 않는다. **현재 노트북에는 학습된 가중치가 없다.** 별도 미세조정 실험에서 생기는 어댑터와 체크포인트는 실행 중 주기적으로 Drive에 저장하고, 새 VM에서 실제 재개할 수 있는지 확인한다. 대용량 기본 모델 파일을 Drive에 복제하는 것은 필수가 아니다.

## 팀원별 Colab 실행 절차

1. GitHub에서 [리스크 노트북](../../models/colab/gemma_risk_labeling.ipynb)을 연다. 비공개 저장소라면 각자 자기 GitHub 권한으로 Colab에 접근을 허용한다. GitHub는 코드 원본이고 실행 VM은 각자 별도다.
2. **런타임 → 런타임 유형 변경**에서 GPU를 선택하고 `nvidia-smi`로 실제 배정 GPU와 메모리를 확인한다. T4는 후보일 뿐 무료 계정에 항상 배정되지 않는다. 무료 Colab은 GPU 종류·할당량·실행 시간이 변하고 유휴 종료가 있다. 한 사람이 여러 계정으로 한도를 우회하지 않는다([Colab FAQ](https://research.google.com/colaboratory/faq.html)).
3. 수집 서버가 새 `apps/trend-api` 코드와 PostgreSQL을 쓰는지 확인한다. `apps/trend-api/scripts/export_risk_sample.py`는 그 환경에서만 실표본을 낼 수 있다. Plan 01의 최신 SQLite 수령·이관이 아직이면 표본의 시점과 한계를 기록한다. 사용자 입력 표는 내보내지 않고 필요한 공개 근거 문장만 CSV로 추출한다. CSV와 같은 이름의 `.env.json`을 팀 Drive의 `inputs`에 함께 보관한다.
4. 입력을 VM에 복사한 뒤 노트북 셀을 순서대로 실행한다. Ollama 버전, `gemma4:12b`의 태그·digest, 프롬프트 해시, 호출 옵션을 서버 기준과 비교한다. 한 팀원이 작은 표본으로 GPU 메모리와 실행 시간을 먼저 측정한다. 서버는 미분류 문장만 묶고 노트북은 최근 문장을 다시 묶으므로 같은 모델이어도 결과가 달라질 수 있다.
5. 각자 다른 프롬프트 안을 별도 실행 ID로 비교한다. 서버 모델과의 일치율은 참고치다. CSV의 `human_*` 칸에 **사람이 독립적으로 판정한 값**을 넣어 오탐·누락과 근거를 비교한다. 합성 표본이나 사람 판정이 없는 일치율을 AI 품질 개선의 증거로 사용하지 않는다.
6. 문장·용어별 결과, 호출 시간, 실행 메타데이터를 `runs/<이름>/<실행 ID>`에 저장한다. 입력 해시, Git 커밋, 모델 digest, GPU, 프롬프트 해시와 검수 상태를 기록한다. Colab 셀 출력과 결과 파일의 원문이 GitHub 노트북에 저장되지 않도록 확인한다.

## 가중치 미세조정 실험 — 별도 노트북

**Colab에서도 Gemma 4 가중치를 학습할 수 있다.** 다만 현재 Ollama 리스크 노트북은 `ollama.chat()`으로 답만 생성하므로 학습이 전혀 일어나지 않는다. 학습에는 정답이 붙은 입력·출력 쌍, 학습 프레임워크, 손실 계산·역전파, 체크포인트 저장 코드가 있는 **별도 노트북**이 필요하다. Google의 [Gemma 텍스트 QLoRA 가이드](https://ai.google.dev/gemma/docs/core/huggingface_text_finetune_qlora)는 Colab에서 기본 모델을 4비트로 읽고 작은 **LoRA 어댑터 가중치**만 학습하는 예를 제공한다. 전체 12B 가중치를 모두 업데이트하는 학습과는 자원 요구가 다르다.

1. 먼저 리스크 분류 또는 사전 언어판처럼 **한 작업**을 고른다. 사람이 판정·수정한 입력과 정답을 모으고 용어·출처 단위로 학습/검증/최종 평가 세트를 분리한다. 모델이 만든 기존 분류를 정답으로 그대로 재사용하거나 같은 문장의 변형을 학습과 평가 양쪽에 넣지 않는다. 현재 `export_risk_sample.py`의 빈 `human_*` 열만으로 학습을 시작하지 않는다.
2. 무료 T4에서 메모리·시간을 먼저 재기 위해 **Gemma 4 E2B + QLoRA** 같은 작은 모델로 시작한다. 공식 가이드의 도입부는 T4 16 GB·Gemma 1B를 기준으로 설명하지만 현재 코드의 기본 모델은 E2B여서, 문서만으로 E2B의 무료 GPU 학습 성공을 보장하지 않는다. 추론용 `gemma4:12b` 파일이 T4에서 로드된다고 해서 **12B 학습도 가능하다고 판단하지 않는다**. 12B 미세조정은 GPU·메모리·실행 시간 실측 후 별도 결정한다. 다른 크기 모델의 어댑터를 12B에 그대로 적용하지 않는다.
3. 학습 노트북에는 기본 모델의 정확한 ID·revision, 데이터 해시, 코드 커밋, QLoRA 설정, 학습 단계·손실·평가 점수, GPU를 기록한다. 추론용 어댑터 파일과 **학습 재개용 체크포인트**를 구분한다. 재개용에는 어댑터뿐 아니라 optimizer·scheduler 상태, 학습 단계, 난수 상태 등 학습기가 요구하는 상태를 함께 저장한다. `checkpoints/<모델>/<실행 ID>`에 주기적으로 완성된 체크포인트를 복사하고, 새 Colab VM에서 어댑터 추론과 학습 재개를 각각 확인한다. 저장 도중 끊긴 파일을 최신 정상 체크포인트로 취급하지 않는다. Git에는 노트북 코드만 넣고 학습 데이터·가중치는 넣지 않는다.
4. **미세조정 전 기본 모델+프롬프트**와 **미세조정 후 기본 모델+어댑터**를 같은 보류 평가 세트에서 비교한다. 근거 일치·리스크 오탐/누락·한국어·영어 표현·국가별 주장·처리 시간과 실패율을 기록한다. 개선이 불분명하면 어댑터를 운영 편집에 사용하지 않고 기본 모델과 검수 경로를 유지한다.
5. 개선이 입증되더라도 어댑터를 Ollama `gemma4:12b`에 자동 적용할 수 있다고 가정하지 않는다. **학습 모델과 실제 편집에 쓰는 모델의 ID·형식·로딩 방법을 맞춘 뒤** 작은 배치로 재현·검증한다. 학습 완료만으로 공개 API나 Cloud SQL의 모델 경로가 바뀌지 않는다.

무료 Colab의 GPU와 실행 시간은 보장되지 않는다([Colab 자원 제한](https://research.google.com/colaboratory/faq.html)). 따라서 미세조정이 중단되거나 품질 향상을 보이지 않아도 Plan 06의 기본 목표인 **검증된 오프라인 초안과 승인 게시**를 진행할 수 있어야 한다. 10월 10일까지 유효한 정답 데이터와 GPU가 준비되지 않으면 학습을 완료했다고 쓰지 않고 실험 결과와 제약을 기록한다.

## 확인된 무료 런타임 자원과 실측 기준

2026-09-29 사용자가 공유한 Colab 화면은 **시스템 RAM 12.7 GB, GPU RAM 15.0 GB, 디스크 112.6 GB**, 현재 사용량에서 **최대 4시간 50분** 실행 가능하다는 안내다. GPU 사용량은 당시 0.0 GB이며 GPU 종류는 화면에 없으므로 `nvidia-smi`로 확인한다. 이 수치는 한 세션의 표시값이고 다음 배정이나 실행 시간을 보장하지 않는다.

- **12B 전체 가중치 학습:** 이 자원에서 현실적인 목표로 잡지 않는다. 일반적인 16비트 표현만으로 약 24 GB의 가중치가 필요하고, 학습에는 기울기·optimizer 상태·중간 계산 메모리가 추가된다. 양자화된 Ollama 추론 파일 크기를 학습 메모리로 계산하지 않는다.
- **작은 모델의 QLoRA:** 가능성을 확인할 별도 실험이다. 먼저 짧은 입력·작은 배치로 20~50 학습 단계를 실행해 CPU/GPU 최대 메모리, 단계당 시간, 설치·다운로드·체크포인트 저장 시간을 잰다. 전체 단계 수와 평가·저장 시간을 합쳐 세션 안에서 가능한 범위를 정한다. 이 단계는 실행 가능성 점검이며 품질 개선의 증거가 아니다.
- **시간 제한:** 학습을 여러 세션에 걸쳐 재개할 수 있도록 저장한다. 마지막 정상 체크포인트 이후의 작업은 중단 시 잃을 수 있으며 다음 GPU 배정도 보장되지 않는다. Drive는 데이터와 학습 상태를 보존할 뿐 GPU RAM을 늘리지 않는다.

## 런타임 종료와 백그라운드 실행

**무료 Colab에는 VM을 무기한 유지하거나 종료를 막는 공식 설정이 없다.** 브라우저 연결 종료와 Colab의 VM 회수는 별개이며, 학습 코드가 실행 중이어도 최대 수명·사용량·자원 제한으로 런타임이 종료될 수 있다([Colab FAQ](https://research.google.com/colaboratory/faq.html)).

| 방법 | 기대할 수 있는 효과와 한계 |
| --- | --- |
| 브라우저 유지·PC 절전 해제 | PC 쪽 연결 유지에 도움을 줄 수 있지만 Colab의 최대 실행 시간·사용량 제한은 그대로다 |
| `nohup`·VM 내부 백그라운드 프로세스 | VM 안에서 프로세스를 실행하는 방식이며, VM 자체가 종료되면 함께 종료된다 |
| 자동 클릭·주기적인 출력 | 최대 실행 시간이나 GPU 회수를 막는 방법으로 의존하지 않는다 |
| Colab Pro+ 백그라운드 실행 | 컴퓨팅 단위가 충분하면 브라우저를 닫아도 실행 중인 노트북을 최대 24시간 실행할 수 있다. 무제한 실행이나 VM 영구 보존은 아니다 |

Pro+ 조건은 [Google의 Colab 상품 설명](https://developers.google.com/workspace/admin/reseller/v1/how-tos/products)과 [실행 시간 안내](https://research.google.com/colaboratory/faq.html)를 기준으로 한다. 일반 Pro 구독이나 컴퓨팅 단위 구매만으로 Pro+의 백그라운드 실행이 제공된다고 가정하지 않는다.

이번 계획은 **무료 Colab에서 짧은 실험을 수행하고 Drive에 진행 상태를 저장·재개하는 방식**을 기본으로 한다. 추론은 완료 항목과 결과를, 미세조정은 앞 절의 학습 재개용 체크포인트를 주기적으로 저장한다. 저장 간격은 실제 저장 시간과 중단 시 허용할 재작업량을 재서 정하며, 마지막 정상 저장본으로 새 VM에서 재개하는 것을 확인한다.

실측 결과 연속 실행 시간이 부족하면 Pro+ 또는 별도 GPU VM의 비용·필요 메모리·실행 시간을 비교해 도입 여부를 결정한다. 현재 계획 변경만으로 유료 구독이나 GPU VM을 생성하지 않는다. 유료 환경에서도 중단에 대비한 체크포인트 저장을 유지한다.

## 구현 순서

1. **입력과 Drive 보관소.** Plan 01의 데이터 시점·근거 ID를 포함한 제한된 공개 표본을 만들고 소유자 Drive 폴더를 팀 계정에 공유한다. 현재 리스크 노트북에 Drive 입력·실행별 결과 저장·부분 결과 저장과 재개를 추가한다. 실표본 실험은 최신 데이터가 준비되는 범위에서 진행하고 Cloud SQL 배포를 기다릴 필요는 없다.
2. **리스크 기준선과 선택적 미세조정 실험.** 현행 `gemma4:12b` 추론의 GPU 메모리·시간과 사람이 판정한 표본의 품질을 측정한다. 미세조정은 별도 노트북에서 작은 모델로 학습·저장·재개 가능성을 먼저 확인한다. E2B 실측을 12B 실측으로 대체하지 않고, 성공·실패·보류 결정을 기록한다.
3. **Colab 편집 배치.** 검증된 뜻과 근거를 받아 사전 언어판·국가별 해석 초안을 만드는 입출력 계약과 배치를 구현한다. 원자료 수집·영상·검색 grounding은 현행 PC 파이프라인에 둔다. 출력에 입력 스냅샷·뜻 버전·모델 ID·프롬프트·검수 상태를 연결하고, Colab이 끊기면 완료된 항목부터 이어서 처리한다. 초안을 Drive에 저장하는 것만으로 승인하지 않는다.
4. **검수와 운영 게시.** 스키마·근거·언어별 뜻 보존을 검사하고 사람이 승인한 결과만 별도 게시 도구로 Plan 05의 Cloud SQL에 반영한다. 게시 도구는 관리되는 PC 등에서 최소 쓰기 권한으로 실행하며 Colab에는 운영 DB 자격증명을 주지 않는다. 배치 ID와 뜻 버전으로 중복·오래된 결과의 덮어쓰기를 막고, 실패 시 마지막 정상 게시본을 유지한다. Cloud SQL Auth Proxy를 쓰더라도 private IP에는 별도 네트워크 경로가 필요하다. 자격증명·사용자 원문·생성 결과 전문은 운영 로그나 Git에 기록하지 않는다.
5. **서비스 분리와 보존·감시.** Cloud Run 웹·API는 PC와 Colab이 꺼져도 게시 자료를 읽어야 한다. 운영 `USE_LOCAL_GEMMA=0`을 기본으로 하고 실시간 자유 서술은 Gemini 또는 사전 기반 규칙으로 구현·검증한다. 해석 캐시 7일·미해결 질문 30일 삭제, 마지막 정상 게시 시각과 오래된 자료 경보는 Plan 05의 독립 예약 작업으로 운영한다.
6. **품질 평가와 시연.** 같은 원자료의 Gemma 초안, 근거 검사, 사람 수정, 게시본을 추적한다. 언어별 뜻 보존·국가별 차이·출처에 없는 주장·처리 시간을 측정해 Plan 09에 넣는다. 미세조정 모델을 실제 채택한 경우에만 해당 어댑터와 전후 평가 결과를 제출 근거로 사용한다.

## 완료 기준

- 팀원이 자기 Colab VM에서 실표본 추론을 실행하고, 입력·결과를 공유 Drive에 저장하며 새 VM에서 다시 불러올 수 있다. GPU·모델·입력·프롬프트 버전을 추적할 수 있다.
- Colab의 Gemma 편집 배치가 검증된 사전 언어판과 국가별 해석 초안을 만들고, 근거·사람 검수를 거친 결과만 별도 게시 도구로 운영 DB에 반영한다.
- 검증되지 않은 초안은 공개 API에 노출되지 않고, 같은 배치를 다시 실행하거나 오래된 배치를 게시하려 해도 뜻 버전과 게시 데이터가 손상되지 않는다.
- PC와 Colab이 꺼져도 공개 지도·사전·게시 결과가 열리고 갱신 시각·오래된 자료 상태가 정확하다. 보존 정리와 운영 건강 점검도 독립적으로 동작한다.
- 실시간 사용자 기능은 Colab이나 PC의 Gemma 없이 작동하며, 사용자 원문은 Colab·팀 Drive·PC로 전달하지 않는다.
- 미세조정은 선택 실험으로 성공·실패·보류 및 실측 제약을 기록한다. 성공이라고 기록하려면 학습 재개와 보류 평가 세트의 전후 비교를 확인한다. 품질이 개선되지 않으면 기본 모델을 유지한다.
- 대표 사례의 근거 일치와 품질을 Plan 09에서 평가해 실제 Gemma 활용 결과를 설명한다. 추론 노트북 실행만으로 가중치를 학습했다고 쓰지 않는다.

## 제외한 계획

- `builder-cup-gemma` Cloud Run GPU 서비스, vLLM 이미지, GPU IAM·인스턴스 경보는 만들지 않는다.
- 무료 Colab을 상시 서버로 쓰거나 Cloud Run API가 Colab·개발자 PC의 Ollama에 실시간 접속하는 경로를 만들지 않는다.
- 무료 GPU RAM 15 GB에서 12B 전체 가중치 학습을 완료하는 것은 목표가 아니다. 작은 모델의 QLoRA도 실측 전 완료 시간·품질을 보장하지 않는다.
- 팀원이 같은 VM이나 모델 메모리를 공유한다고 가정하지 않는다. 각자 실행하고 승인된 입력·결과·체크포인트만 공유한다.
- 모델 크기·GPU·프롬프트가 다른 실험의 품질·비용·속도를 동일한 결과로 취급하지 않는다.
