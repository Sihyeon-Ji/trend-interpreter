## 목적

Trend Interpreter는 사전을 만드는 여러 단계에서 Gemma 4를 사용한다. 하지만 이 작업은 모두 수집 서버(PC)나 Kaggle 노트북의 오프라인 배치에서 진행되고,
배포본에는 결과만 게시된다. 그래서 배포된 서비스만 쓰는 사람(심사위원·팀원)은 **어느 값을 Gemma가 붙였는지, Gemma가 실제로 도는지** 확인하기 어렵다.

이 계획은 [Gemma 운영 라이브 분류 제안](../AI-개발/Gemma-운영-라이브-분류-제안.md)을 실행 계획으로 옮긴다. 제안서의 '라이브 분류 버튼'에
두 가지를 더해 세 단계로 나눈다.

| 단계 | 보여 주는 것 | GPU | 공개 사전에 쓰나 |
| --- | --- | --- | --- |
| **0. Gemma 기록 표시** | 배치가 이미 남긴 Gemma 결과와 모델 이름을 화면에 드러낸다 | 필요 없음 | 읽기만 한다 |
| **1. 라이브 분류** | 사전 항목의 버튼 하나로 Gemma가 최신 기사 문장을 지금 분류하는 모습 | 운영 Gemma 서비스 | 쓰지 않는다 (화면 응답만) |
| **2. 관리자 수동 실행** | 관리자가 Gemma 단계 하나를 골라 용어 몇 개에 직접 돌려 보는 기능 | 운영 Gemma 서비스 | 검수 큐에만 쓴다 |

0단계만으로도 "Gemma가 무엇을 만들었는가"는 보인다. 1·2단계는 "Gemma가 지금 돌아가는 순간"을 배포본 안에서 보여 준다.
세 단계 모두 **자동 실행이 없고**, Gemma가 꺼져 있거나 실패해도 공개 서비스는 마지막 게시본으로 동작한다.

## 지금 Gemma가 하는 일

`USE_LOCAL_GEMMA=1`이고 로컬 모델이 떠 있으면 `pipeline/gemini.py`의 `structured`·`generate`가 텍스트 작업을 `pipeline/local_llm.py`로 보낸다.
실제 호출은 `interpreters/local_chat.py` 한 곳을 거친다. 모델은 `GEMMA_LOCAL_MODEL`(기본 `gemma4:12b`)이다.

| 단계 (`run_pipeline.py` 이름) | Gemma가 하는 일 | 결과가 저장되는 곳 | 모델 기록 | 지금 화면에 보이나 |
| --- | --- | --- | --- | --- |
| `classify` | 수집 제목을 트렌드 유형으로 분류 | 분류 결과 | 확인 필요 | 결과만 |
| `spot` | 쇼츠 제목·커뮤니티 글·해석 실패 메시지에서 '뜻을 찾아볼 표현' 제안 | 후보 | 없음 | 후보 목록만 |
| `crosscheck` | 사전 뜻과 참고 위키 설명 비교 서술 | `crosscheck_log`, 검수 큐 | `crosscheck_log.model` | 관리자 검수 화면 |
| `risk` | 근거 문장마다 뉘앙스·위험 유형·그 뜻으로 쓰였는지 | `evidence_labels` | `evidence_labels.model` | 수준·이유만. 문장별 분류는 안 보임 |
| `translate` | 검증된 뜻의 언어판 | 뜻 텍스트 | 엔진 이름 반환(`gemma-local`) | 언어판만 |
| `fit` | 광고 쓰임 낱말(느낌·쓰임·분야·말투) | `term_fit` | `term_fit.model` | 추천 점수에 섞여 안 보임 |
| 요청 때 `explain` | '쉽게 풀어 쓰면' 재작성 (`gemma_rewrite`) | 저장 안 함 | 없음 | 운영은 `USE_LOCAL_GEMMA=0`이라 쓰지 않음 |

운영에서 요청 때 Gemma를 부르는 경로는 없다(`USE_LOCAL_GEMMA=0`). 운영에 Gemma 서비스를 둘지는 **아직 정하지 않았고 팀이 협의 중이다**.
이 계획은 두기로 할 경우의 안이며, 공개 요청 경로에는 계속 Gemma를 두지 않고 사람이 누르는 버튼 두 곳에서만 부른다.

## 0단계. Gemma 기록 표시 (GPU 없음)

가장 싸고 먼저 할 일이다. 이미 DB에 있는 모델 기록을 읽어 보여 준다.

| 화면 | 보일 것 |
| --- | --- |
| 사전 항목 | 리스크 판정 아래 "근거 문장 분류 보기": 문장별 뉘앙스·위험 유형·제외 여부와 `evidence_labels.model`, 분류 시각. 규칙 판정(`risk.judge`)이 어느 문장을 셌는지 표시 |
| 사전 항목 | 광고 쓰임 낱말(`term_fit`)과 모델 이름. 언어판마다 만든 엔진 |
| `/admin/status` | 단계별 마지막 실행의 모델 호출 수·걸린 시간(`local_llm.stats()`)과 사용 모델. Gemma를 쓴 단계는 표시를 따로 단다 |
| 새 화면 `/about/gemma` (공개) | 위 쓰임 지도를 사용자 말로 옮긴 설명, 단계별 Gemma 결과 건수, 대표 항목 링크 몇 개 |

할 일은 다음과 같다.

- 번역 결과에 엔진 이름을 저장하는지 확인하고, 없으면 번호 붙은 마이그레이션으로 열을 더한다. `classify`·`spot`의 모델 기록도 같은 방식으로 확인한다.
- 단계 실행 기록에 `local_llm.stats()`의 호출 수·시간과 모델 이름을 남긴다. 문장·모델 출력 원문은 로그에 남기지 않는다.
- 근거 문장은 이미 공개된 근거만 보인다. 새로 저장하는 원문은 없다.

## 1. 라이브 분류 버튼

동작·원칙·비용 추정은 [제안서](../AI-개발/Gemma-운영-라이브-분류-제안.md)의 1~7절을 따른다. 요약하면 다음과 같다.

1. 사전 항목의 '지금 다시 분류해 보기'를 누르면 API가 운영 Gemma 서비스를 깨운다.
2. `collectors/news_rss`로 최신 기사 제목을 모으고 `match.mentions`로 표제어가 든 문장만 남긴다(최대 `risk.PER_TERM`개, 5개 미만이면 모델을 부르지 않음).
3. `pipeline/risk.py`와 같은 프롬프트·출력 형식으로 문장을 분류하고, `risk.judge`와 같은 규칙으로 수준을 정한다.
4. 배치 결과와 나란히 보이고, 다르면 다르다고 표시한다. 결과는 공개 사전에 쓰지 않는다.

API는 `POST /terms/{term_id}/live-risk`다. 권한·하루 한도·용어별 10분 캐시는 제안서 3절의 안(A 관리자만 / B 누구나 한도 안에서)을 팀이 정한 뒤 넣는다.
실행 기록 표에는 시각·용어 ID·문장 수·걸린 시간·결과 수준만 남긴다.

## 2. 관리자 수동 실행

제안서에는 없는 부분이다. 팀원·심사 데모에서 "배치 파이프라인의 Gemma 단계도 클라우드에서 돈다"를 보이려는 것이다.
전체 파이프라인을 운영에 올리지 않는다는 [Plan 05](05-trend-cloud-run-deployment.md)의 결정은 그대로 두고, **범위를 좁힌 수동 실행**만 연다.

| 항목 | 정한 것 |
| --- | --- |
| 위치 | `/admin/status`에 '수동 실행' 패널. 검수자 계정만 |
| 고를 수 있는 단계 | `risk`, `fit`, `translate`, `crosscheck`. 수집 키가 필요 없고, 이미 운영 DB에 있는 근거·뜻만 쓰는 단계다 |
| 대상 | 용어 1~5개를 고른다. 전체 실행은 없다 |
| 실행 방식 | API가 Cloud Run Job 실행을 한 번 요청한다(`gcloud run jobs execute`와 같은 API 호출). Scheduler는 두지 않는다. 한 번에 하나만 돈다 |
| 결과 | 공개 값을 바로 바꾸지 않는다. `risk`·`fit`·`translate`의 새 값은 검수 큐에 제안으로 올리고, `crosscheck`는 지금처럼 검수 큐에 올린다. 사람이 승인해야 게시된다 |
| 화면 | 실행 중 단계, 용어별 처리 수, 걸린 시간, 모델 이름, 이전 값과 새 값의 차이 |

`risk`·`fit`·`translate`를 검수 큐에 올리려면 [Plan 12](12-dictionary-crosscheck.md)의 제안 종류(`review_queue.kind`)에 종류를 더해야 한다.
이것이 부담스러우면 첫 판은 **결과를 화면에만 보이고 저장하지 않는** 미리보기로 시작하고, 검수 큐 연결은 다음 판으로 미룬다.

## 운영 Gemma 서비스

1·2단계가 같은 서비스를 쓴다.

| 항목 | 정한 것 | 이유 |
| --- | --- | --- |
| 실행기·모델 | Ollama(수집 서버와 같은 버전) + `gemma4:12b` | 배치와 같은 모델·실행기여야 결과를 비교할 수 있다 |
| 위치 | Cloud Run GPU 서비스, L4 1개, asia-southeast1 | 도쿄에는 Cloud Run GPU가 없다 |
| 인스턴스 | 최소 0 · 최대 1 | 평소 비용 0, 동시에 눌러도 GPU는 하나 |
| 공개 범위 | 비공개. API 런타임 서비스 계정과 수동 실행 Job 계정만 호출 권한 | 외부에서 GPU를 직접 부르지 못하게 |
| 가중치 | 이미지에 포함 | 켜질 때 인터넷에서 받지 않게 |
| 프로젝트 | **별도 GCP 프로젝트 + 그 프로젝트 전용 지출 한도 (권장)** | 한도에 닿아도 Gemma만 멈추고 웹·API는 산다 |
| 경보 | GPU 인스턴스가 30분 넘게 켜져 있으면 알림 | 누른 뒤 꺼지지 않는 경우를 잡는다 |

코드에서 바꿀 곳은 다음과 같다.

- `interpreters/local_chat.py`는 Ollama 주소가 `localhost:11434`로 정해져 있다. Ollama 주소를 환경 변수로 받게 하고, 비공개 Cloud Run을 부를 때 ID 토큰을 `Authorization` 헤더에 붙인다.
- `local_llm.available()`의 5분 캐시가 '꺼져 있음'을 오래 들고 있지 않게, 버튼 경로에서는 깨우기 요청을 먼저 보내고 제한 시간(4분) 안에서 다시 확인한다.
- 공개 요청 경로(`explain`, 추천, 생성)는 계속 `USE_LOCAL_GEMMA=0`이다. 운영 Gemma를 부르는 곳은 1단계 API와 2단계 Job 두 곳뿐이다.
- 인프라는 `infra/gcp`에 모듈로 더하고 `terraform fmt -check`와 `terraform validate`로 확인한다.

## 비용

단가와 계산은 [제안서](../AI-개발/Gemma-운영-라이브-분류-제안.md) 4절을 쓴다(L4 1개 기준 시간당 약 $1.05 하한, 한 번 누를 때 약 15분 ≈ $0.26, 실측 전).
2단계 수동 실행은 관리자만 쓰므로 하루 5회를 상한으로 두고, 1단계 한도와 합쳐 월 지출 한도를 넘지 않게 잡는다.
실제 청구는 아래 측정에서 Billing으로 확인한다.

## 구현 순서

1. **0단계** (10-07): 모델 기록 확인·보강 → 사전 항목의 근거 문장 분류 보기 → `/admin/status` 모델 표시 → `/about/gemma`. 검증은 `docker compose run --rm --build check`와 e2e.
2. **시험 배포** (10-09): 별도 프로젝트에 Gemma 서비스를 올리고 제안서 7절의 항목(켜지는 시간, 처리 시간, 배치와의 일치율, 청구, 한도 분리)을 잰다. 합격하지 못하면 1·2단계를 멈추고 0단계와 영상 시연으로 대신한다.
3. **1단계** (10-11): `POST /terms/{term_id}/live-risk`, 실행 기록 표 마이그레이션, 웹 버튼·진행 표시·실패 안내.
4. **2단계** (10-12): 수동 실행 Job, 관리자 패널, 첫 판은 미리보기. 검수 큐 연결은 여유가 있을 때.
5. 데모 영상 장면과 [README](../../README.md)의 Gemma 설명을 결과에 맞춰 고친다.

## 완료 기준

- 배포본의 사전 항목에서 Gemma가 붙인 문장별 분류와 모델 이름을 볼 수 있다(0단계).
- Gemma 서비스가 꺼진 상태에서 버튼을 누르면 준비 → 분류 → 판정까지 제한 시간 안에 끝나고, 배치 결과와 나란히 보인다(1단계).
- 관리자가 고른 용어에 `risk` 단계를 수동 실행하면 결과와 이전 값의 차이가 보이고, 공개 값은 바뀌지 않는다(2단계).
- Gemma 서비스를 멈추거나 지출 한도에 닿게 해도 웹·API가 정상 응답한다.
- 운영 로그와 실행 기록에 문장·모델 출력 원문이 없다.
- 헬스 체크 통과만으로 완료로 보지 않는다. 실제 버튼 실행 한 번과 그 청구를 확인한 뒤 완료로 기록한다.

## 하지 않는 것

- 정기 수집·분류, Scheduler, 전체 파이프라인 Job
- 수집 키가 필요한 단계(`collect`, `naver`, YouTube 해석 등)의 운영 실행
- 버튼·수동 실행 결과를 검수 없이 공개 사전에 반영하는 것
- 이용자가 입력한 문장을 Gemma로 분류하는 것
- 최소 인스턴스 1로 늘 켜 두는 것
- vLLM 등 수집 서버와 다른 실행기로 바꾸는 것
