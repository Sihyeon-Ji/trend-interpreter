## 2026-10-03 점검

이번에는 GCP 원격 상태·Billing·콘솔 만료 시각을 조회하지 않았다. 아래 과거 RUNNABLE 기록을 현재 상태로 재표시하지 않는다. Plan 05의 운영 백업/복원과 연결하고, 10-20~26의 비용 결정·수동 전환 일정은 유지한다.

근거·검증 범위와 구현 적절성은 [10-03 점검 보고서](archive/구현-완료도-실측-점검-2026-10-03.md)를 따른다. 아래 날짜별 결과는 당시 기록으로 보존한다.

### 10-03 원격 조회와 복원 리허설

같은 날 이후 읽기 전용으로 다시 조회했다. 인스턴스는 `RUNNABLE`이고 자동 백업·PITR·삭제 보호가 꺼져 있으며 백업은 0건이다. DB는 기본 `postgres` 하나뿐이고 디스크 사용량은 약 100MB여서 **보존할 앱 데이터는 없다.** 무료 체험 인스턴스는 삭제 시 최종 백업 외의 백업·복원을 지원하지 않는다. 정확한 만료 시각은 API 응답에 없어 10-20~22 콘솔 확인 일정을 유지한다.

위 2단계의 `pg_dump` 보관·로컬 복원 절차는 고정 snapshot으로 리허설했다. 41개 표 이관, 48개 표·659,707행·스키마의 dump→복원 일치를 확인했다. 결과와 유료 전환 직후 적용할 보호 설정안·staging 연결안은 [Cloud SQL 복원 리허설](../개발환경/Cloud-SQL-복원-리허설.md)에 있다. 5단계의 "자동 백업·시점 복구가 의도대로 꺼져 있는지"와 Plan 17의 백업/PITR 요구는 서로 다르므로, 전환 경로를 정할 때 함께 결정한다.

사용자 결정(10-03): 새 인스턴스 사양은 **공유 코어 소형**, Cloud SQL 월 상한은 **약 $30**이다. 공유 코어는 기존 Enterprise Plus 인스턴스를 제자리 전환할 수 없으므로 아래 일정의 실행은 **B 경로**가 된다. 옮길 앱 데이터가 없어 B의 데이터 이전 위험은 snapshot 재적재로 대신한다. 일정(10-20~22 견적·만료 확인, 10-24 확정, 10-26 실행)은 유지한다. 그때까지 체험 인스턴스의 `trend_staging` DB를 staging으로 쓴다. 백업·PITR은 지금 켜지 않고 10-24 확정 때 다시 판단하며, 새 인스턴스에는 삭제 보호를 켠다.

## 목표와 현재 상태

`stunning-crane-508614-c1` 프로젝트의 `trend-project`가 체험 종료 뒤에도 Trend 서비스를 중지시키지 않도록,
종료 **전**에 비용을 비교하고 사람이 콘솔에서 전환을 실행한다. 공모전 제출 마감은 **2026-10-18**이므로 제출 뒤
실제 시연·심사 일정을 확인하면서 전환하되, 만료 직전까지 미루지 않는다. 이 계획은 데이터 적재나 유료 전환을
지금 실행하는 지시가 아니다.

2026-09-29 읽기 전용 조회에서 인스턴스는 `RUNNABLE`, 도쿄(`asia-northeast1`), PostgreSQL 18, Enterprise Plus
`db-perf-optimized-N-8`(8 vCPU·64 GB), 스토리지 100 GB다. 자동 백업과 시점 복구는 꺼져 있다. 사용자가 콘솔에서
“무료 체험 기간이 30일 후에 종료됩니다” 문구를 확인했다. **정확한 만료 시각과 남은 일수는 실행일에 인스턴스 개요에서
다시 확인한다.** 현재 앱 연결, 실제 데이터 크기, 부하, 유료 전환 후 예상 청구액은 아직 검증되지 않았다.

Cloud SQL의 **유지보수 설정은 엔진·시스템 업데이트의 시간대**를 정한다. 체험 만료나 유료 전환을 예약하지 않는다.
공식 체험 안내에는 원하는 사양으로의 자동 유료 전환 설정이 없다. 만료 전에 업그레이드하지 않으면 인스턴스가 요청
처리를 멈추고, 데이터는 추가 90일 동안 보관된 뒤 삭제 예정 상태가 된다. 유료 전환은 콘솔의 **지금 업그레이드**로
직접 실행한다([무료 체험 안내](https://docs.cloud.google.com/sql/docs/postgres/free-trial-instance),
[유지보수 안내](https://docs.cloud.google.com/sql/docs/postgres/maintenance)).

## 비용과 서비스 연속성 비교

| 경로 | 실행 방법 | 연결·비용 특성 |
| --- | --- | --- |
| **A. 기존 인스턴스 유료 전환 – 기본 경로** | `trend-project`에서 **지금 업그레이드**를 누른다. 업그레이드 완료 후 같은 인스턴스를 Enterprise Plus N2의 작은 후보 `db-perf-optimized-N-2`(2 vCPU·16 GB) 등 실제 부하에 맞는 사양으로 조정한다 | Google은 체험→유료 전환 자체를 데이터 손실·중단 없는 전환으로 안내한다. 이후 사양 축소는 별도 작업이므로 연결을 감시한다. 업그레이드와 축소 사이에는 기존 8 vCPU·64 GB·100 GB 사양의 요금이 발생한다. 인스턴스 연결 이름은 유지된다 |
| **B. 새 소형 인스턴스로 이전 – 비용이 A의 상한을 넘을 때** | 도쿄에 Enterprise 공유 코어(예: `db-f1-micro`)·필요한 스토리지로 새 인스턴스를 만들고, 검증한 덤프를 복원해 Cloud Run의 DB 연결을 새 인스턴스로 바꾼다 | 공유 코어는 더 낮은 비용 후보지만 SLA 대상이 아니고 메모리·연결 수를 실제 부하로 검증해야 한다. 이전 중 쓰기를 멈추거나 동기화 경로를 마련해야 하며, 새 인스턴스의 연결 정보·IAM·Secret·배포 변경이 필요하다. 읽기 서비스의 무중단은 별도 검증 없이는 보장하지 않는다 |

현재 Enterprise Plus 인스턴스를 Enterprise **공유 코어로 제자리 전환할 수 없다**. 제자리로 Enterprise로 바꿀 때는
전용 코어 또는 N4가 후보이며 더 긴 중단이 생길 수 있다. 따라서 B는 새 인스턴스와 데이터 이전을 전제로 한다
([에디션 변경 제한](https://docs.cloud.google.com/sql/docs/postgres/upgrade-in-place)). A의 작은 N2 후보도 실제 비용이
적절하다는 뜻은 아니다. 공유 코어의 SLA·메모리 제약은 [인스턴스 설정 안내](https://docs.cloud.google.com/sql/docs/postgres/instance-settings)에서 확인한다.
크기와 부하를 확인한 뒤 [공식 가격 계산기](https://cloud.google.com/products/calculator)에서
**도쿄·PostgreSQL·단일 영역·730시간/월·100 GB 스토리지**를 넣어 계산한다. B는 새 인스턴스의 스토리지와
이전 중 두 인스턴스가 동시에 운영되는 시간을 포함한다. 백업·데이터 전송·Cloud Run 비용은 각각 별도 항목으로 확인한다.

비용 비교표에는 최소한 **A의 유료 전환 전 사양, A의 축소 후 사양, B의 새 인스턴스, 이중 운영 시간**을 적는다.
기존 100 GB는 전환만으로 줄어들지 않는다. 필요한 경우 별도의 [스토리지 축소 기능](https://docs.cloud.google.com/sql/docs/postgres/about-storage-shrink)을
검토하되 최소 허용 크기·성능 영향·Terraform 미지원 여부를 먼저 확인하고 전환 당일의 필수 작업으로 묶지 않는다.
Billing 예산 알림은 지출을 자동으로 막지 않으므로, 실제 보고서와 함께 비용을 확인한다
([예산 알림 안내](https://docs.cloud.google.com/billing/docs/how-to/budgets)).

## 실행 전 조건과 검증

1. 콘솔에서 남은 체험 시간, 결제 계정, 현재 `RUNNABLE` 상태를 확인한다. 새 리소스 또는 유료 전환을 실행하기 전에
   **최신 견적과 월 비용 상한을 사람에게 보여 주고 최종 결정을 받는다.** 비용 상한이 정해지지 않으면 유료 전환을 실행하지 않는다.
2. Plan 05의 앱·DB 연결이 완료됐는지 확인한다. 사전·검수 기록 등 중요한 데이터가 있다면 비밀번호나 원문을 로그에
   남기지 않고 `pg_dump`로 보관한 뒤 별도 로컬 PostgreSQL에 복원해 확인한다. 덤프는 Git에 넣지 않는다.
3. A를 택하면 콘솔에서 **지금 업그레이드**를 실행하고 체험 배너가 사라졌는지 확인한다. 이후 결정한 작은 사양으로
   변경하고 작업 완료까지 기다린다. 사양 변경 중 Cloud SQL 상태와 Trend 웹·API의 실데이터 요청을 반복 확인한다.
   Enterprise Plus의 첫 축소는 대체로 짧은 중단을 목표로 하지만 완전한 무중단을 약속하지 않는다
   ([Cloud SQL 가용성 안내](https://docs.cloud.google.com/sql/docs/availability)).
4. B를 택하면 새 인스턴스에서 데이터·마이그레이션·권한·연결을 사전 검증하고, 쓰기 중지 또는 동기화 절차를 정한 뒤
   트래픽을 전환한다. 공유 코어의 연결 한도에 맞춰 `DB_POOL_SIZE`·Cloud Run 동시성·최대 인스턴스 수를 다시 정한다.
   읽기·쓰기와 재시작 검증 전에는 기존 인스턴스를 삭제하지 않는다. B 경로에서는 기존 체험
   인스턴스를 유료로 전환하지 않으며, 만료 전에 새 인스턴스에서 서비스가 동작해야 한다.
5. 어느 경로든 인스턴스 상태, 공개 웹의 사전·지구본·메시지 해석, API의 익명 접근 거부, 쓰기·재시작 후 데이터
   유지, 보존 작업을 확인한다. 자동 백업·시점 복구 설정이 의도대로 꺼져 있는지도 재확인한다. Cloud Billing 보고서는
   반영이 늦을 수 있으므로 다음 날 다시 확인한다.

## 실패하거나 비용이 예상보다 높을 때

- A의 업그레이드는 끝났지만 사양 축소가 실패하면, 기존 DB 연결을 유지하고 원인을 확인해 축소를 다시 시도한다.
  그동안 큰 사양의 요금이 쌓이므로 당일 과금과 다음 날 Billing 보고서를 확인한다. 설정 변경이 끝났다고 판단하기
  전에 실제 인스턴스 사양을 다시 조회한다.
- B의 전환 검증이 실패하면 기존 체험 인스턴스가 살아 있는 동안 DB 연결을 원래 값으로 되돌린다. 체험 만료가
  임박했다면 중단을 피할 수 있는 A의 유료 전환을 비용 상한과 함께 다시 결정한다.
- 만료일까지 어느 경로도 완료하지 못하면 서비스가 중지될 수 있음을 운영 기록에 남긴다. 90일 데이터 보관은
  서비스 가용성을 보장하지 않는다. 데이터나 사용 중인 서비스를 확인하지 않고 인스턴스를 삭제하지 않는다.

전환 완료 뒤 [Plan 05](05-trend-cloud-run-deployment.md)와 [GCP 운영 문서](../운영/GCP-운영.md)에 실제 사양,
비용 확인일, 체험 종료 상태, 연결 대상, 백업 결정을 갱신한다. 콘솔에서 만든 `trend-project`는 현재 Terraform 외부
자원이므로 같은 이름의 생성 리소스를 추가하지 않는다.
