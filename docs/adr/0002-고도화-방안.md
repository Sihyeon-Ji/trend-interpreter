# ADR 0002. 데이터 파이프라인과 해석 모델 고도화 방안

상태 **확정** · 결정일 **2026-09-28** · 관련 [ADR 0001 서비스 방향](0001-서비스-방향.md) · [파이프라인 기록](../트렌드/파이프라인.md) · [아키텍처](../운영/시스템-아키텍처.md)

## 배경

팀에서 네 가지 고도화 방안(멀티모달 파이프라인, 밈 생애주기 추적, Graph RAG, 멀티 에이전트)을 제안했습니다.
2026-09-28에 코드와 수집 데이터(용어 613개, 근거 약 1만 500건)를 기준으로 이미 있는 것과 비어 있는 것을 확인했습니다.

| 제안 | 이미 있는 것 | 비어 있는 것 |
| --- | --- | --- |
| 멀티모달 | Gemini가 쇼츠를 직접 보고 화면 글자·음성·밈·확산 이유·리스크를 뽑음(해석 64건) | 사진 업로드 입력 |
| 생애주기 | 주간 언급량 규칙으로 7단계 판정(`lifecycle.py`) | 용어 613개 중 406개가 `unknown`. 뜨는 중·정점은 7개. 플랫폼 순서 기준 판정 없음 |
| Graph RAG | `edges` 표(검색어→인물·위키·근거·용어), 도구 기반 사전 조회 루프 | 용어와 용어 사이의 관계 |
| 멀티 에이전트 | ADK 파이프라인 에이전트 4개, 영상 리스크 항목, 세대·나라 맞춤 풀어쓰기 | 리스크 판정, 마케터용 생성 |

근거 출처 종류별 건수는 커뮤니티 4,556, 뉴스 3,834, 위키·웹 1,301, 쇼츠 448, 네이버 데이터랩 366입니다.

## 결정

### 1. 생애주기: 데이터 보강과 출처 순서 기반 판정 (우선순위 1)

- 먼저 `unknown` 비율을 줄입니다. 원인인 주간 언급 추적(`track` 단계) 대상과 주기를 넓힙니다.
- 기존 언급량 규칙에 **출처가 처음 등장한 순서**를 더합니다. 이미 수집하는 근거로 판정할 수 있는 세 단계만 씁니다.

  | 단계 | 판정 근거 |
  | --- | --- |
  | 태동 | 커뮤니티 근거만 있음 |
  | 확산 | 쇼츠·유튜브 근거가 생기고 언급량이 오름 |
  | 주류·쇠퇴 | 뉴스 근거가 늘고 언급량이 정점 대비 줄어듦 |

- 제안의 "트위터·인스타그램 확산" 단계는 해당 플랫폼을 수집하지 않으므로 쓰지 않습니다.
- 판정은 규칙 코드가 하고, LLM은 "쇠퇴기라 캠페인에 쓰기엔 식상할 수 있음" 같은 이유만 서술합니다.

### 2. 리스크: 용어별 리스크 필드와 근거 기반 판정 (우선순위 2)

- 용어에 리스크 수준(없음·주의·사용 자제)과 이유를 저장합니다. 스키마 변경은 번호 붙은 마이그레이션으로 합니다.
- 판정 근거는 영상 해석의 `risk_flags`, 부정 뉘앙스 근거의 비율, 검수자 결정입니다. LLM이 단독으로 "안전함"을 붙이지 않습니다.
- 대시보드의 긍정·부정 뉘앙스는 근거 문장 단위로 Gemma가 분류하고, 용어 단위 집계는 코드가 합니다.

### 3. 멀티 에이전트: 요청당 호출 수를 줄인 역할 분담

제안은 분석·검증·페르소나 에이전트를 요청마다 따로 부르는 구조였습니다. Gemma 호출은 로컬 실측으로 한 번에 8~13초였고,
개발자 PC 모델은 SaaS 요청의 가용성을 책임질 수 없습니다. 그래서 Gemma는 공개 자료를 미리 편집하고 요청 시에는 게시본을 씁니다.

| 역할 | 방식 | 시점 |
| --- | --- | --- |
| 분석(뜻·맥락) | 기존 로컬 파이프라인의 Gemini 조사·Gemma 초안·검증 게이트 | 수집·편집 시(배치) |
| 리스크 판정 | 규칙 코드 + 로컬 Gemma 분류 결과 | 수집·편집 시(배치) |
| 추천 | 사전·생애주기·리스크 데이터 조회 | 요청 시(모델 호출 없음) |
| 생성(카피·대본·썸네일) | Gemini 한 번의 구조화 호출 | 요청 시 |
| 사전 대조 검사 | 게시된 뜻·리스크와 규칙 코드. 의미 판단이 필요한 경우 Gemini로 별도 평가 | 요청 시 |

무거운 판단은 로컬 배치로 미리 해 두고, 요청 시에는 기본적으로 생성 한 번과 코드 검사를 합니다. 추가 모델 검사가 실제로 필요하면 품질 평가를 거쳐 넣습니다. 파이프라인 배치의 ADK 에이전트 팀은 그대로 둡니다.

### 4. 멀티모달: 사진 업로드 추천

- 사용자가 올린 사진 한 장을 Gemini가 읽어 제품 종류·분위기·색·장면을 구조화된 설명으로 바꿉니다.
- 그 설명과 목표 지역으로 사전에서 밈을 고르고, 생애주기와 리스크로 순위를 정합니다.
- 짤 이미지를 대량으로 모아 DB에 쌓는 방식은 하지 않습니다. 저작권과 저장 비용 대비 효과가 낮습니다.
- 사진은 요청 처리에만 쓰고 저장하지 않습니다. 운영 로그에도 남기지 않습니다.
- 별도 Vision API는 쓰지 않습니다. Gemini가 이미지 이해를 직접 합니다.

### 5. 관계 그래프: 용어 간 관계 (여유가 있을 때)

- 기존 `edges` 표에 용어와 용어 사이의 관계(`DERIVED_FROM` 파생, `RELATED_TO` 관련)를 추가합니다. 별도 그래프 DB는 쓰지 않습니다.
- 관계 후보는 LLM이 제안하되, **한 근거 문장에 두 용어가 함께 나올 때만** 저장합니다.
- 사용자가 변형된 유행어를 입력하면 관계를 따라 원조 용어의 뜻과 맥락을 함께 가져옵니다.
- BGM·춤 노드는 [ADR 0001](0001-서비스-방향.md)에 따라 이번 제출에서 제외합니다.

## 하지 않기로 한 것

- 요청마다 여러 Gemma 에이전트를 순서대로 부르는 구조
- 그래프 DB(Neo4j, Spanner Graph) 도입. PostgreSQL `edges` 표로 충분합니다
- 짤 이미지 대량 수집, 썸네일 OCR 적재
- 수집하지 않는 플랫폼(X, 인스타그램, 틱톡)을 근거로 한 생애주기 단계
- 벡터 검색 도입. 사전 규모(수백~수천 개)에서는 기존 키워드·유사 문자 검색으로 충분하며, 규모가 커지면 다시 검토합니다

## 결과와 후속 작업

- 각 단계의 실행 계획은 위 구현 순서에 연결한 `docs/plans/` 문서에 있습니다.
- 새 표와 컬럼은 `storage/migrations/`의 번호 붙은 SQL 파일로 추가합니다.
- 생성 기능은 기본 개발 환경에서 모델을 부르지 않으므로, mock 응답으로 화면과 계약을 먼저 검증하고 실제 품질은 별도로 평가합니다.
- 기대 효과(추천 적합도, 카피 품질)는 아직 측정하지 않았습니다. 평가 사례를 만들어 제출 전 한 번 측정합니다.
