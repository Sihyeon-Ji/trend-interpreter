# 승인 배치 게시 도구

작성일 **2026-10-07** · 상태 **로컬 저장소·CLI·웹 검수 구현, Job 실행 파일·기본 비활성 Terraform 구현, SQL 권한 로컬 검증 완료, 운영 적용 미완료**

Plan 17의 변경 배치를 서비스 DB에 초안으로 보관하고, 검수자가 확인한 정확한 해시의 배치만 한 트랜잭션으로 게시한다. Plan 19의 전체 DB 갱신과는 다른 작업이다. 현재 도구는 `apps/trend-api/scripts/publication.py`, 계약은 `storage/publications.py`, 새 표는 migration `020_approved_publications.sql`이다.

## 입력과 권한

입력 JSON은 `batch_id`, `snapshot_id`, `snapshot_sha256`, `model_id`, `prompt_version`, `rule_version`, `items`를 포함한다. 배치에는 표제어별 항목을 최대 1,000개 넣는다. 같은 ID에 다른 내용을 다시 넣을 수 없다. SHA-256은 정규화한 JSON 전체와 각 항목에 따로 기록한다.

항목은 `term_id`, 확인 당시의 `expected_meaning_id`와 변경할 `meaning`, `translations`, `country_notes`, `fit` 중 하나 이상을 포함한다. 새 표제어는 `new_term`과 `meaning`, `expected_meaning_id: null`이 필요하다. 새 표제어·별칭의 정규화된 이름은 같은 배치와 기존 사전에서 충돌하면 안 된다. 근거는 `evidences`, 인용은 근거 URL 목록인 `citations`로 전달한다.

번역·국가별 설명·추천 속성은 `derived_from_sha256`으로 생성에 사용한 뜻을 고정한다. 새 뜻이면 `publications.digest(MeaningDraft)`를, 기존 뜻이면 현재 Meaning에서 MeaningDraft 필드만 뽑은 객체의 digest를 쓴다. 이를 모델이 임의로 계산하게 하지 않는다. 국가별 현지 밈은 해당 근거 문장 안에 실제 이름이 있어야 한다.

`snapshot_sha256`와 모델·프롬프트·규칙 버전은 생산자가 제공하는 계보 정보다. 이 도구만으로 외부 snapshot 파일의 진위나 모델 품질을 검증하지 않는다. 원문 사용자 문장·자격 증명을 입력에 넣지 않는다.

검수는 `ACCOUNTS`의 실제 검수자 계정과 대화형 비밀번호로 인증한다. DB에 쓸 권한이 있는 운영자용 CLI이며, 일반 이용자에게 DB나 CLI를 제공하는 방식이 아니다. 웹의 `/admin/batches`에서도 목록·변경 비교·승인/거절을 할 수 있다. 웹 서버는 서명된 세션의 검수자 여부를 확인하고, 결정자 이름을 세션에서 가져와 서버 토큰과 함께 API에 전달한다. 다른 사이트에서 온 결정 요청은 거부한다. stdout에는 ID·해시·상태·건수·게시 시각만 기록하고, 전체 초안은 독점 생성하는 권한 `0600` 파일에 쓴다. 초안 파일은 Git에 넣지 않는다.

## 실행 순서

아래 명령은 PostgreSQL·계정 설정이 준비된 API 실행 환경에서 쓴다. 로컬 검증에는 별도 DB를 사용한다. `db.connect()`는 새 migration을 적용하므로 운영 DB에서는 검증된 호환 release로 먼저 준비해야 한다.

```bash
cd apps/trend-api
uv run --locked python scripts/publication.py stage --file /private/batch.json
uv run --locked python scripts/publication.py inspect --batch-id batch-example --out /private/review.json
uv run --locked python scripts/publication.py review --batch-id batch-example --sha256 VERIFIED_PAYLOAD_SHA256 --user REVIEWER --decision approve
uv run --locked python scripts/publication.py publish --batch-id batch-example
```

검수자는 파일의 변경 내용·검증 경고·근거와 `payload_sha256`을 확인한다. 거절할 때는 `--decision reject`를 쓴다. 검증 게이트의 경고가 있으면 기본 승인은 거부하며, 사람이 근거를 확인하고 예외를 승인할 때만 `--allow-gate-exceptions`를 명시한다. 무효한 뜻·파생 판 불일치·누락된 인용·사람 결정 보호 위반은 예외 승인으로 우회하지 못한다.

## 게시와 실패

- 준비·승인은 공개 뜻이나 보드에 쓰지 않는다. 게시 시점에 뜻 판, 표제어·근거·파생 출력의 기준 해시를 다시 확인한다.
- 사람 승인 뜻, 사람 작성 파생 출력(`model=team`), 사람 리스크 결정, 제외 상태, 수정 검수 대기를 보호한다. 기준이 바뀌면 충돌로 남기고 새 배치를 준비한다.
- 뜻 변경은 새 판으로 기록하고 이전 파생 출력을 무효화한다. 같은 입력의 재실행과 동시에 들어온 중복 게시는 원래의 게시 ID를 반환한다.
- 뜻·번역·국가별 설명·추천 속성, 보드·대시보드·색인은 한 트랜잭션으로 갱신한다. 설명 캐시는 비운다. 활성 `publication_id`는 마지막에 바꾸며, 항목 하나나 캐시 갱신이 실패해도 전체 변경을 롤백한다.
- 일시 실패는 승인 기록을 유지한 `failed`로 남아 같은 배치를 다시 게시할 수 있다. 충돌은 `conflict`이며 재승인 없이 강제로 덮어쓰는 옵션은 없다. 실패 기록에는 예외 종류나 정해진 코드만 넣는다.
- `/meta`와 유지보수의 신선도는 활성 성공 게시 시각을 따른다. 첫 배치 게시 전에는 기존 파이프라인 게시 시각을 사용한다. 게시 뒤 이전 파이프라인의 자동 쓰기를 차단하는 운영 전환은 별도 완료 조건이다.

Plan 19 overlay는 성공 게시된 표제어의 뜻·번역·국가별 설명·추천 속성과 네 게시 표를 보존한다. 새 표가 없는 이전 DB도 인수할 수 있다. 전체 DB 갱신으로 서비스 승인 결과가 수집 사본의 자동 결과로 돌아가지 않도록 하는 연결이다.

## 검증과 잔여

검사는 실제 PostgreSQL의 임시 스키마에서 승인 전 비공개, 불변 해시, 항목·캐시 실패의 전체 롤백, 뜻 판·사람 결정 충돌, 중복 동시 게시, 활성 게시 보존, 사람 작성 파생 출력 보호, 새 이름 충돌, 읽기 전용 검수 파일과 비검수자 인증 거부를 확인한다. Plan 19 overlay는 게시 결과 보존과 migration 이전 DB 인수를 확인한다.

영어 번역 생산자 포장은 아래 경로를 구현했다. 다시 쓴 뜻 포장은 아래 팀 후속 도구를 따른다. 국가별 설명·추천 속성 생산자 연결, 전용 DB 역할·Cloud Run Job·예약 실행, 운영 migration·실제 게시·복구 시험은 남았다. 새 표제어의 이용량·최초 관측 날짜를 이 도구가 만들지 않는다. 사람의 뜻·번역 품질 검수도 테스트 통과로 대체하지 않는다.

검증 결과: `docker compose run --rm --build check` 종료 코드 0 – 데이터 20·API 429·배포/복구 26·relay 10·웹 단위 21개, lint·production build 통과. 이후 비밀번호 입력 보호와 `/meta` 연결 검사를 보완한 게시/CLI 검사 20개도 Compose check 이미지에서 통과했다. `docker compose run --rm --build e2e` 종료 코드 0, 45개 통과. `git diff --check` 통과. 실제 운영 DB·유료 모델·GCP 자원은 변경하지 않았다.

## 웹 검수 연결

검수자는 관리자 메뉴의 **변경 묶음**에서 최근 배치를 50개씩 읽는다. 상세 화면은 현재 뜻·언어별 뜻과 제안을 나란히 보여 주고, 근거·인용·국가별 설명·추천 속성·입력/모델 버전·해시를 확인하게 한다. 준비 뒤 기준 자료가 바뀌면 승인 버튼을 잠그며 거절은 가능하다. 전체 확인 체크와 경고 예외 체크를 별도로 받고, 본 배치의 정확한 해시를 보낸다. 승인 후 상태는 **게시 대기**이며 웹에는 게시 버튼이 없다.

API의 `/review/batches`·상세·결정은 모두 서버 토큰을 요구한다. 웹 데이터 함수와 결정 라우트도 각각 검수자 세션을 확인한다. 응답은 `private, no-store`, 백엔드 요청은 `no-store`다. 브라우저가 결정자 이름이나 게시 지시를 넣어도 승인 계약에 전달하지 않는다. API는 기존 검수 방식과 같이 인증된 웹 서버가 전달한 계정을 신뢰한다. 예시 모드는 실제 배치가 없음을 표시하고 실제 목록이나 승인을 흉내 내지 않는다.

검증 범위는 PostgreSQL API 검사와 웹 결정 핸들러의 인증·위조 계정 제거·동일 출처·프록시 Host 처리, 예시 모드 E2E의 메뉴·비공개 페이지/결정 접근 차단이다. 실제 운영의 배치 비교·승인·게시 리허설은 남아 있으며, 예시 E2E를 그 완료 근거로 쓰지 않는다.

### 로컬 API 모드 화면 실측 (10-07)

실제 production 이미지의 별도 웹/API 서비스를 띄우고 `publication_flow_qa_20261007` 임시 PostgreSQL 스키마에 합성 배치 2개를 준비했다. 실제 웹 브라우저에서 비로그인 접근 차단, 검수자 세션의 목록·현재 뜻/제안 비교·확인 체크·승인, 승인 뒤 기존 공개 뜻 유지, 위조한 결정자 이름 제거를 확인했다. 별도 게시 실행 뒤 공개 사전과 `/meta`의 활성 게시 ID·신선도가 갱신됐고, 같은 배치 재실행은 같은 ID, 오래된 두 번째 배치는 충돌로 종료했다. 390px 화면의 가로 넘침이 없었으며 데스크톱/모바일 screenshot을 확인했다. 시험용 서비스·스키마는 종료 후 삭제했다. 합성 자료·mock 시험이며 운영 게시나 실제 AI 품질 근거가 아니다.

웹 연결 최종 검증: 전체 Compose check 종료 코드 0(API 435개·배포/복구 26개 포함), 마지막 웹 보완 뒤 단위 26개·lint·production build 통과, E2E 46개 통과. 별도 API 모드 브라우저 시험에서 승인·위조 결정자 차단·공개 조회·활성 게시·상세 메뉴 표시·390px 화면을 확인했다. 운영 배포는 실행하지 않았다.

## 버전이 고정된 영어 번역 입력·결과 포장 (10-07)

`publication.py export-translations`는 읽기 전용 PostgreSQL 연결의 한 REPEATABLE READ snapshot에서 선택한 승인 표제어의 뜻을 내보낸다. 입력 JSONL에는 표제어 ID·표기, 원래 뜻 판 ID, MeaningDraft 원문·해시, 번역 대상 MeaningText, 인수 snapshot ID·SHA-256이 들어간다. 최대 1,000개, 중복·미승인 항목은 거부한다. 입력 텍스트와 뜻 원문의 해시도 서로 일치해야 한다. snapshot ID·SHA는 운영자가 확인한 인수 기록을 전달하는 값이며, 이 명령이 현재 DB 전체와 외부 사본의 동일성을 검증하는 것은 아니다.

```bash
cd apps/trend-api
uv run --locked python scripts/publication.py export-translations \
  --term-id TERM_ID --term-id ANOTHER_TERM_ID \
  --snapshot-id VERIFIED_SNAPSHOT_ID --snapshot-sha256 VERIFIED_SNAPSHOT_SHA256 \
  --out /private/terms.jsonl
uv run --locked python scripts/publication.py pack-translations \
  --input /private/terms.jsonl --results /private/translations.jsonl \
  --run /private/run.json --batch-id translation-example --out /private/batch.json
uv run --locked python scripts/publication.py stage --file /private/batch.json
```

Kaggle의 `models/kaggle/translate/translate_meanings.py`는 새 입력의 판 ID·해시를 각 결과에 그대로 남긴다. 입력 파일 SHA, 실제 모델 digest, 번역 코드 SHA도 결과 행과 `run.json` 양쪽에 기록한다. 재개 시 입력 파일·뜻 판·모델/코드가 다른 기존 결과를 섞지 않는다. 진행 stdout에는 순서·시간·실패 표시만, 실패 자료에는 예외 종류만 기록한다. 모델 실행과 비공개 Dataset 업로드는 이 변경에서 수행하지 않았다.

`pack-translations`는 DB나 모델에 접속하지 않는다. 원래 입력 파일 해시, 모든 결과의 표제어·원문·뜻 판·내용 해시·모델 digest·번역 코드 SHA를 대조한다. 중복·알 수 없는 표제어·누락 결과·빈 번역은 거부한다. 실패 행이 있으면 기본은 전체 중단이며, `--skip-failed`를 명시하면 그 행만 제외하고 제외 건수를 stdout에 기록한다. 이 경우에도 입력 항목마다 성공/실패 결과가 있어야 한다. 원문·결과를 stdout에 내지 않으며 배치 파일은 권한 `0600`으로 독점 생성한다.

배치의 `model_id`는 실제 로컬 모델과 digest, `prompt_version`은 번역 코드 SHA, `rule_version`은 현재 게시 규칙 코드 SHA를 기록한다. 포장만으로는 승인이나 게시가 되지 않는다. 준비 때 현재 뜻 판이 달라졌으면 충돌하며, 사람 작성 번역과 사람 결정 보호도 기존 게시 검증을 거친다.

**10-06의 기존 69건 시험 결과는 원래 뜻 판과 행별 모델/입력 계보가 없으므로 이 경로에 그대로 승격할 수 없다.** 현재 뜻 판을 임의로 붙이는 호환 옵션은 제공하지 않는다. 새 버전 입력으로 재실행하고 사람이 뜻·번역 품질을 확인해야 한다. 형식·해시 검사 통과는 번역 품질 통과가 아니다.

번역 생산자 연결 검증: `docker compose run --rm --build check` 종료 코드 0 – 데이터 20·API 451·배포/복구 26·relay 10·웹 단위 26개, lint·production build 통과. 합성 입력/번역의 포장→준비→승인→게시, 잘못된 원문·판·입력/모델 계보·중복·누락·명시적 실패 제외, 읽기 전용/오프라인 CLI·비공개 파일·GPU 없이 생산자 기록/재개를 확인했다. 사용자 화면·라우트 변경이 없어 E2E를 재실행하지 않았으며 앞선 46개 결과를 유지한다. 실제 번역 실행·Kaggle 업로드·운영 DB 쓰기·GCP 변경은 하지 않았다.

## 다시 쓴 뜻 포장 (10-07)

`scripts/pack_meaning_rewrites.py`는 사람이 검토 표에서 ok 로 확정한 '다시 쓴 뜻'(Plan 16의 시험, 연구 DB 사본에 있음)을 `meaning` 항목의 ChangeBatch 로 포장한다. DB·모델을 바꾸지 않는다.

- 입력: 검토 CSV(`label(ok/fix)` 가 ok 인 행), 다시 쓴 뜻이 든 연구 DB(`DATABASE_URL`), 같은 snapshot 을 손대지 않은 **기준 사본**(`--baseline-url`). `expected_meaning_id` 는 기준 사본의 현재 뜻 판, `evidences` 는 다시 쓰기가 새로 찾은 근거만, `citations` 는 그 가운데 근거 주소에 있는 것만 넣는다. 사람이 확인한 뜻·검수 대기·바뀌지 않은 말은 뺀다.
- 계보: `--snapshot-id`·`--snapshot-sha256`(인수한 `trend-latest.db` 의 SHA-256), `--model-id`(로컬 모델과 digest), `--prompt-version`·`--rule-version`(저장소 커밋).

```bash
cd apps/trend-api
DATABASE_URL=postgresql://.../trend_research_1006b uv run --locked python scripts/pack_meaning_rewrites.py \
  --review ../../artifacts/meaning-review/rewrite-trial/review-all.csv \
  --baseline-url postgresql://.../trend_research_stage \
  --snapshot-id 20261006T224515-8b2a19c --snapshot-sha256 <trend-latest.db SHA-256> \
  --model-id "local:gemma4:12b@<digest>" --prompt-version research.OFFLINE_PROMPT@f4a41e1 --rule-version audit.rule_overrides@f4a41e1 \
  --batch-id meaning-rewrite-20261007 --out /private/batch.json
```

**로컬 시험(10-07).** 같은 10-06 22:45 snapshot 의 손대지 않은 사본(`trend_research_stage`)에 5개를 포장해 `stage` → `inspect` → 승인 → `publish` 를 끝까지 돌렸다. 준비는 `draft` 로 통과했고, 5개 중 2개(고길동 등)에 검증 게이트 경고가 붙었다 – "표현이 아니라 인물·일반 단어로 판단됨", "모델이 든 웹 근거에 용어가 없음". 경고가 있으면 기본 승인은 `gate_review_required` 로 막히고, 사람이 근거를 읽고 `--allow-gate-exceptions` 로 승인해야 한다. 게시 뒤 다섯 말의 뜻은 새 판(`verified_human`, 결정자 이름)이 됐고 상태는 `verified` 다.

**게시하면 그 말의 언어판(translations)·추천 속성(term_fit)·국가별 설명이 지워진다.** 옛 뜻에서 만든 파생 출력이라 그렇다. 영어판은 그 뒤 수집 서버의 `translate` 나 Kaggle 번역으로 다시 만들어야 하며, 그때까지 영어 화면은 한국어 원문을 보인다. 데모 준비도(리스크 없음 + 영어판)에 잠깐 영향이 있다.

운영에 쓰려면 남은 것: 운영 DB 에 migration `020` 적용(호환 release 로), 관리자 화면(`/admin/batches`)에서 승인, 게시 실행 주체. 10-10 운영 갱신(Plan 19)에 맞춘다. 10-07 에 운영 DB 를 읽기 전용으로 기준 삼아 42개를 다시 포장했고(`--baseline-url` 에 운영 URL, 도구의 기준 연결은 `connect_read_only`), 운영 DB 에 020 이 없어 준비 단계에서 멈췄다(Plan 16 '운영 적용 전 확인').

## 게시 Job 실행 파일·인프라 설정 (10-07)

`apps/trend-api/scripts/publication_job.py`는 정확한 배치 ID 한 개를 받아 기존 승인 게시 함수를 호출한다. `--batch-id` 또는 `PUBLICATION_BATCH_ID`가 없거나 형식이 맞지 않으면 DB에 접속하기 전에 종료한다. 승인 전·거절된 배치는 게시되지 않고, 성공 배치의 재실행은 기존 게시 ID를 반환한다. 모델을 부르거나 승인 결정을 만드는 기능은 없다. stdout은 게시 ID·배치 ID·시각·건수만, 오류는 정해진 코드만 기록한다.

```bash
cd apps/trend-api
uv run --locked python scripts/publication_job.py --batch-id APPROVED_BATCH_ID
```

Job은 `db.connect_existing()`을 사용해 DDL 없이 연결하고, DB의 migration 번호/체크섬 집합이 실행 이미지의 파일과 정확히 일치하는지 확인한다. 미적용·변조·더 새 버전이 있으면 종료하며 Job이 migration을 적용하지 않는다. migration은 호환 release 준비 단계에서 별도로 실행한다. 일반 운영자용 `publication.py`의 준비/검수 기능과 이 책임을 분리했다.

`infra/gcp/hybrid/publication.tf`는 별도 publisher 서비스 계정, Cloud SQL client 권한과 전용 secret 하나의 접근 권한, 고정 API 이미지의 Job을 정의한다. `publisher` 변수 기본값은 `null`이어서 Job·추가 IAM은 생기지 않는다. 활성화 입력의 secret은 `trend-<환경>-publisher-database/versions/<숫자>`만 허용한다. API의 공유 DB secret·계정·프론트 토큰·Gemini/GPU 자격 증명은 Job에 주지 않는다.

Job은 task 1개·재시도 0회, CPU 1·메모리 2Gi·300초, private VPC와 Cloud SQL socket을 사용한다. 모델은 mock/요청 비활성, GPU도 비활성이며 SQL 문장 240초·잠금 대기 10초 제한을 둔다. 기본 배치 ID는 빈 값이므로 실행마다 운영자가 승인된 ID를 지정해야 한다. 자동 게시 Scheduler는 만들지 않는다. root Terraform의 운영 Job 실패 경보에는 `trend-production-publication`도 포함했다. 운영의 실제 알림 전달은 별도 확인이 필요하다. 운영 규모의 시간·메모리 실측은 아직 하지 않았다.

**아래는 Job 기반 구현 시점의 기록이며, SQL 역할의 로컬 검증은 다음 후속 절에서 완료했다.** 별도 secret은 SQL 권한 제한의 증거가 아니다. 전용 PostgreSQL 로그인/역할의 게시 표·캐시 쓰기, 배치 승인 변경·사용자 원문 조회·DDL 금지를 실제 권한으로 검증하는 작업은 남았다. 현재 Job 기능 검사는 임시 스키마의 개발 소유자 연결을 사용했다. 그 권한 시험과 운영 migration·staging Job 실행·게시 후 공개 조회/복구 검증 전에는 운영 구축 완료로 올리지 않는다. 이 변경에서는 Terraform apply·GCP 자원 생성·Job 실행·운영 DB 변경을 수행하지 않았다.

게시 Job 기반 최종 검증: 전체 Compose check 종료 코드 0 – 데이터 20·API 458·배포/복구 26·relay 10·웹 단위 26개, lint·production build 통과. Job 검사 7개는 배치 미지정/잘못된 ID, migration 미적용·변조·더 새 버전, 승인 전 차단·중복 재실행, 원문 없는 오류를 확인했다. `docker compose run --rm infra-check` 종료 코드 0 – root/hybrid `terraform fmt -check`·`terraform validate`, hybrid mock 시험 10개 통과. 사용자 화면 변경이 없어 E2E는 재실행하지 않았으며 앞선 46개 결과를 유지한다. 제한된 SQL 역할 시험·실제 GCP Job·알림/복구 검증은 아직 수행하지 않았다.

팀 후속 커밋 `90a1494`까지 통합한 뒤 다시 검증했다. 전체 Compose check 종료 코드 0(API 461개·웹 단위 26개·lint/build 포함), E2E 종료 코드 0·46개 통과. 쓰임/한국어 뜻 검사와 사람이 ok한 다시 쓴 뜻 포장 도구도 통합본에 보존했다. Terraform 코드에는 추가 충돌/변경이 없으며 위 root/hybrid 검사·mock 10개 결과를 유지한다.

## 전용 PostgreSQL 역할·승인 경계 (10-07 후속 완료)

migration `021_publisher_permissions.sql`은 게시 역할 등록 표와 배치 UPDATE 보호 trigger를 추가한다. 등록된 게시 역할은 이미 승인된 `approved`/`failed` 배치의 상태를 `published`/`failed`/`conflict`로 마무리하고 실패 코드만 바꿀 수 있다. 배치 본문·해시·원본 snapshot·검수자·검수 시각은 바꾸지 못한다. 초안·거절 배치를 직접 승인하거나 게시 상태로 바꾸는 SQL도 거부한다. 기존 migration 파일은 수정하지 않았다.

`configure_publisher_role.py`는 **이미 만들어진 전용 역할**에 서비스 스키마의 게시 관련 표·캐시 쓰기와 캐시 재생성에 필요한 수집/사전 표 읽기만 부여한다. 역할이나 비밀번호를 만들지 않는다. 기존 역할의 서비스 표 직접 권한을 교체하며 다른 역할·PUBLIC 권한은 바꾸지 않는다. superuser·DB/역할 생성·복제·RLS 우회 권한, 다른 역할 멤버십, DB/서비스 스키마 생성 권한, 서비스 표 소유권이 있는 역할은 거부한다. 역할 이름은 영문 소문자로 시작하는 소문자·숫자·밑줄, 최대 63자다.

```bash
cd apps/trend-api
# migration 021까지 적용한 DB의 소유자 연결로, 별도 기존 역할을 설정한다.
uv run --locked python scripts/configure_publisher_role.py --role trend_publisher
# DATABASE_URL을 이 전용 로그인으로 설정한 실행 환경에서 게시한다.
uv run --locked python scripts/publication_job.py --batch-id APPROVED_BATCH_ID
```

Job은 시작할 때 실제 현재 역할의 제한·등록 상태를 다시 검사한다. `lookups`·`reader_prefs`·`gemini_calls`에는 권한을 주지 않는다. `explain_cache`는 게시 뒤 무효화를 위한 DELETE만 허용하고 SELECT는 금지한다. 이후 추가된 사용자 표 권한은 테이블뿐 아니라 열 단위 권한까지 검사해 실행을 막으며, 다른 역할 멤버십이 추가돼도 막는다. 허용된 사전·수집 자료와 검수 기록에는 SELECT가 있으므로 이 역할을 익명/일반 이용자나 생산자에게 제공하지 않는다.

서비스 스키마의 CREATE/ALTER/TRUNCATE는 허용하지 않는다. DB의 기본 PUBLIC TEMP 권한을 바꾸거나 클러스터 전체를 잠그는 도구는 아니다. 게시 역할에는 사전 자료 쓰기가 필요하므로 사람이 승인한 뜻·리스크·제외 상태와 항목/판 충돌 보호는 계속 신뢰하는 게시 코드가 검사한다. SQL 권한 분리만으로 임의 SQL의 모든 사전 변경을 막았다고 주장하지 않는다.

새 DB로 옮기는 Plan 19 전환에서는 migration 적용 뒤 **그 DB에 전용 역할 권한을 다시 설정**하고 검사한다. 연구 snapshot의 역할 이름을 복사해 자동 활성화하지 않는다. Job은 migration 집합 불일치·등록되지 않은 역할·과도한 권한을 거부하므로 이 준비가 빠지면 게시를 진행하지 않는다.

검증은 임시 PostgreSQL 스키마와 임시 NOLOGIN 역할의 SET ROLE을 사용한 실제 SQL 권한 시험이다. 승인 배치 게시·중복 재실행·캐시 갱신, SQL로 초안/거절/검수자/본문/해시 변경 거부, 사용자 원문/장부 조회·서비스 DDL·TRUNCATE 거부, 나중에 추가된 열 권한·역할 멤버십 거부, 게시 실패의 전체 롤백과 재시도를 확인했다. Job 검사도 이제 소유자 대신 제한된 역할로 실행한다. 임시 역할·스키마는 시험 뒤 제거한다.

운영의 로그인/비밀번호·전용 secret 준비, migration 021 적용, 실제 로그인 연결·staging Cloud Run Job·실제 게시/알림/복구 확인은 남는다. 이 변경에서 운영 DB·GCP 자원은 변경하지 않았다.

후속 최종 검증: `docker compose run --rm --build check` 종료 코드 0 – 데이터 20·API 480·배포/복구 26·relay 10·웹 단위 26개, lint·production build 통과. API에는 SQL 권한 시험 19개와 게시 Job 검사 7개가 포함된다. `docker compose run --rm --build e2e` 종료 코드 0 – 46개 통과. 이번 후속 변경은 Terraform 코드를 바꾸지 않았으며 앞선 root/hybrid 검사·mock 10개 결과를 유지한다.
