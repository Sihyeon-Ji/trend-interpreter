# 개발 명령어 모음

[한국어 README](../../README.kr.md) | [처음 설치하기](처음-설치.md)

**평소에는 이 문서를 보고 필요한 명령만 실행하면 됩니다.**
Docker를 켠 뒤 `compose.yaml`이 있는 저장소 루트에서 실행하세요.
아래 명령은 Trend 앱(`apps/trend-api`, `apps/trend-web`)과 알림 중계기용이며 `prototype/`과 별도 GPU 서버는 포함하지 않습니다.

## 가장 자주 쓰는 명령

| 하고 싶은 일 | 실행할 명령 | 결과 |
| --- | --- | --- |
| 개발 시작 | `docker compose up -d` | PostgreSQL·API·웹을 백그라운드로 실행 |
| 준비 완료까지 기다리며 시작 | `docker compose up -d --wait` | API·웹이 정상 상태가 될 때까지 대기 |
| 실데이터 모드로 시작 | `DATA_MODE=api docker compose up -d` | 웹이 예시 데이터 대신 로컬 API를 읽음 |
| 실행 상태 확인 | `docker compose ps` | 서비스 상태와 연결 포트 표시 |
| 최근 로그부터 계속 보기 | `docker compose logs -f --tail 100` | 최근 100줄부터 실시간 로그 표시 |
| API 로그만 보기 | `docker compose logs -f --tail 100 api` | API 오류·재시작 상태 확인 |
| 웹 로그만 보기 | `docker compose logs -f --tail 100 web` | Next.js 오류·화면 변경 감지 확인 |
| 개발 환경 종료 | `docker compose down` | 개발 컨테이너와 네트워크 제거, 소스·이미지·DB 볼륨은 유지 |

개발 화면은 **http://localhost:3000**, API 문서는 **http://localhost:8000/docs**, API 상태는 **http://localhost:8000/health**입니다.
로그를 보다가 `Ctrl+C`를 누르면 로그 보기만 끝납니다. 서버 종료는 `down`을 사용하세요.

다른 checkout을 동시에 띄울 때는 `COMPOSE_PROJECT_NAME`과 `DEV_API_PORT`·`DEV_WEB_PORT`를 구분합니다.
기본 포트는 8000·3000이며 모든 개발 공개 포트는 루프백에 바인딩합니다.
[격리 실행 예시](macOS-설치-진단.md#5-별도-checkout을-독립적으로-검증하기)와
[Compose 프로젝트 이름 규칙](https://docs.docker.com/compose/how-tos/project-name/)을 참고하세요.

## 화면 모드와 데이터

| 모드 | 켜는 방법 | 웹이 읽는 것 |
| --- | --- | --- |
| 예시 데이터(기본) | `docker compose up -d` | `apps/trend-web/lib/sample/`의 내장 예시. API가 비어 있어도 화면이 열림 |
| 실데이터 | `DATA_MODE=api docker compose up -d` | `http://api:8000`이 읽는 PostgreSQL 데이터(`postgres_data` 볼륨) |

실데이터 모드에서 사전과 보드가 비어 보이면 API에 데이터가 없는 것입니다. 파이프라인은 API 컨테이너 안에서 실행합니다.

```bash
docker compose exec api python scripts/run_pipeline.py --stages collect,board
```

수집 단계 중 YouTube·Naver 등 키가 필요한 수집기는 키가 없으면 건너뜁니다. 기본 개발 환경은
`MODEL_REQUESTS_ENABLED=false`라 Gemini를 부르는 단계는 실행하지 않으며, 로컬 Gemma가 필요한 단계는
Ollama가 없으면 실패로 기록되고 다음 단계로 넘어갑니다. 단계 설명은 [파이프라인 기록](../트렌드/파이프라인.md)에 있습니다.
`postgres_data` 볼륨은 `down`으로 지워지지 않습니다. 처음부터 다시 만들려면 볼륨 삭제 옵션을 명시적으로 사용합니다.

### PostgreSQL 사용 규칙

| 항목 | 값 |
| --- | --- |
| 서비스 | `db` (`postgres:18.6-bookworm`), 호스트 포트 없음 |
| 개발 계정 | `trend` / `trend`, 데이터베이스 `trend` (루프백 전용 개발값) |
| API 연결 | `DATABASE_URL=postgresql://trend:trend@db:5432/trend` (Compose가 설정) |
| 볼륨 | `postgres_data` (데이터), `trend_data` (시드·평가 결과) |
| 연결 풀 | API는 `DB_POOL_SIZE`(기본 8)개까지 연결을 재사용. 요청이 DB를 처음 쓸 때 빌리고 응답 뒤 반납 |

저장소 코드는 `apps/trend-api/src/trend_agents/storage/db.py`를 거쳐 PostgreSQL에 접근합니다. 호출부는 `?` 자리표시자와
`INSERT OR REPLACE` 같은 짧은 문장을 그대로 쓰고, 어댑터가 psycopg 형식과 `ON CONFLICT`로 바꿉니다. 테스트는 연결마다
임시 스키마를 만들어 서로 간섭하지 않습니다.

SQL을 직접 보려면 `db` 컨테이너 안에서 `psql`을 씁니다.

```bash
docker compose exec db psql -U trend -d trend -c '\\dt'
```

### 스키마 변경 (마이그레이션)

표를 새로 만들 때는 DDL(`storage/dictionary_store.py`, `storage/store.py`)에 `CREATE TABLE IF NOT EXISTS`로 추가합니다.
**이미 있는 표를 바꾸거나 데이터를 보정할 때는** `apps/trend-api/src/trend_agents/storage/migrations/`에 다음 번호의 SQL 파일을 추가합니다.

```text
001_term_aliases.sql
002_add_term_region_index.sql   ← 새 파일은 이렇게 다음 번호로
```

API나 파이프라인이 DB에 처음 연결할 때 아직 적용하지 않은 파일만 번호순으로 한 번씩 적용하고, `schema_migrations` 표에 번호·이름·SHA-256을 남깁니다.
**이미 적용된 파일은 고치지 마세요.** 내용이 바뀌면 checksum이 달라져 연결 자체를 거부합니다. 고칠 내용은 새 번호의 파일로 추가합니다.
적용 기록은 다음 명령으로 봅니다.

```bash
docker compose exec db psql -U trend -d trend -c 'SELECT * FROM schema_migrations ORDER BY version'
```

### 사용자 입력 문장 보존 기간

메시지 해석 캐시(`explain_cache`)는 **7일**, 사전에 없던 표현(`lookups`)은 마지막으로 물은 지 **30일**이 지나면 지웁니다.
파이프라인의 `collect.retention` 단계와 유지보수 스크립트가 같은 함수를 부릅니다. 유지보수 스크립트는 수집 없이 정리만 하고,
마지막 정상 게시(지도·대시보드)가 12시간보다 오래됐는지도 봅니다. 운영에서는 PC와 상관없이 예약 실행하고, 로컬에서는 직접 실행합니다.

```bash
docker compose exec api python scripts/maintenance.py
```

결과는 한 줄(`maintenance status=… explain_cache_deleted=… lookups_deleted=…`)이고 종료 코드는 0 정상, 1 실패, 2 게시본이 오래됨입니다.
로컬 DB에 파이프라인 기록이 없으면 2가 나오는 것이 맞습니다.

### SQLite 시절 데이터 옮기기

이전 프로토타입의 `data/trend.db`가 있다면 빈 DB에 한 번 옮깁니다. 이미 있는 행은 건너뛸 뿐 새 파일의 값으로 바꾸지 않으므로,
최신 파일로 다시 옮길 때도 빈 DB에서 시작합니다. `--fresh`는 대상 `terms`에 행이 있으면 아무것도 옮기지 않고 끝납니다.

```bash
docker compose up -d --wait db
docker compose cp apps/trend-api/data/trend.db api:/workspace/apps/trend-api/data/trend.db
docker compose exec api python scripts/migrate_sqlite_to_postgres.py --sqlite data/trend.db --fresh
```

두 번째 명령은 `api` 컨테이너가 떠 있어야 합니다(`docker compose up -d`). 표마다 복사한 행 수를 출력하며,
기본키가 없는 기록 표(`pipeline_runs` 등)는 대상이 비어 있을 때만 복사합니다. 옮긴 뒤 `terms.diffusion`을 용어 JSON에서 채우고
별칭 표를 다시 만듭니다. PostgreSQL 기본키 색인은 한 항목이 2,704바이트까지라, 주소가 2,048바이트보다 긴 뉴스는 수집하지도 옮기지도 않습니다.
Cloud SQL로 보낼 사본은 `--skip-user-data`로 해석 캐시(`explain_cache`)와 계정별 설정(`reader_prefs`)을 뺍니다.
기본 `postgres_data` 볼륨을 지우지 않고 따로 옮겨 보는 절차는 [Plan 01](../plans/archive/01-import-latest-trend-data.md)에 있습니다.

## 수정한 내용을 반영할 때

| 변경한 내용 | 해야 할 일 |
| --- | --- |
| `apps/trend-web/`의 `app`·`components`·`lib`·`public`·`proxy.ts`·`next.config.ts` | 저장만 하면 브라우저에 자동 반영 |
| `apps/trend-api/src/`·`scripts/`의 Python | 저장만 하면 API 자동 재시작 |
| 패키지 목록·lockfile | `docker compose up -d --build` |
| `Dockerfile.dev`, 앱별 `Dockerfile` | `docker compose up -d --build` |
| Compose 서비스 설정 | `docker compose up -d --build` |
| 코드는 그대로이고 API 프로세스만 재시작 | `docker compose restart api` |
| 코드는 그대로이고 웹 프로세스만 재시작 | `docker compose restart web` |

`restart`는 이미지를 다시 빌드하거나 바뀐 Compose 설정을 적용하지 않습니다.
의존성이나 설정이 바뀌었다면 `up -d --build`를 사용하세요.
기본 개발 서비스는 호스트 `.env`를 컨테이너에 전달하지 않습니다.

## 검사와 테스트

| 확인할 것 | 실행할 명령 | 실행 조건 |
| --- | --- | --- |
| API 테스트·릴리스 테스트·알림 중계기 테스트·웹 lint·웹 프로덕션 빌드 | `docker compose run --rm --build check` | 개발 서버가 꺼져 있어도 가능 |
| 실제 서비스 의존성 취약점 | `docker compose run --rm security-check` | API·relay·web lockfile만 검사, `prototype/` 제외. 외부 취약점 DB에 연결 |
| 브라우저에서 화면 열림 | `docker compose run --rm --build e2e` | 배포와 같은 production API·웹 이미지를 자동으로 빌드·시작 |
| Terraform 설정 | `docker compose run --rm infra-check` | 클라우드 리소스를 생성하지 않음 |
| Compose 설정 문법 | `docker compose config --quiet` | 설정 내용을 출력하지 않고 검사 |

`check`는 검사 중 하나라도 실패하면 중단합니다. `db`를 먼저 켜고 API 테스트를 임시 스키마에서 실행합니다. 현재 API 테스트 86개, 릴리스·복구 테스트 9개(환경상 1개 건너뜀),
알림 중계기 테스트 10개가 있으며 개발에 따라 개수는 바뀝니다. E2E는 개발 화면 3000에 연결해 지구본 첫 화면과
사전 화면이 열리는지 확인합니다. 첫 브라우저 테스트는 이미지에 Chromium을 설치하므로 시간이 더 걸릴 수 있습니다.
검사 컨테이너는 `--rm`으로 종료 후 제거되지만, E2E가 시작한 개발 서버는 남아 있습니다.
검사 통과는 실제 Gemini 연결이나 AI 품질을 확인한 결과가 아닙니다.

이미 실행 중인 API 컨테이너에서 Python 테스트만 빠르게 다시 실행할 수도 있습니다. 같은 `db`를 쓰지만 임시 스키마라 개발 데이터를 건드리지 않습니다.

```bash
docker compose exec api pytest -q tests
```

이 명령은 전체 `check`의 대체가 아닙니다. 실패한 브라우저 테스트의 파일을 보관하는 방법은
[설치 가이드](처음-설치.md#verify)를 참고하세요.

## 로그와 계정

API와 파이프라인은 로그를 **표준 출력**으로만 냅니다. 로컬에서는 `docker compose logs -f api`로 보고, Cloud Run에서는
Cloud Logging에 JSON 한 줄(`severity`, `message`)로 남습니다. 형식은 `LOG_FORMAT=text|json`으로 바꿀 수 있습니다.
로그에는 사용자가 입력한 문장, 모델 출력, 비밀값을 넣지 않습니다.

검수자·이용자 계정은 API 컨테이너 안에서 만듭니다.

```bash
docker compose exec api python scripts/set_account.py --user 이름 --reviewer
docker compose exec api python scripts/set_account.py --list
```

비밀번호는 **이 명령의 출력에 한 번만** 표시되고 파일에 저장되지 않습니다. `.env`에는 해시만 남습니다.
본인에게 직접 전달한 뒤 터미널 출력은 남기지 마세요.

## 배포 이미지 확인

CI가 만드는 것과 같은 프로덕션 이미지를 로컬에서 빌드하고 smoke 검사를 돌릴 수 있습니다.

```bash
docker build -t builder-cup-trend-api:local apps/trend-api
docker build -t builder-cup-trend-web:local apps/trend-web
bash scripts/container-smoke.sh builder-cup-trend-api:local builder-cup-trend-web:local
```

smoke 검사는 API `/health`와 웹 첫 화면(예시 데이터 모드)만 확인하고 컨테이너를 정리합니다.
GCP 배포가 아니며 Cloud Run 리소스를 만들지 않습니다.

## 계약 파일(schema) 갱신

`apps/trend-api/src/trend_agents/schemas.py`를 바꾸면 웹의 타입도 다시 생성합니다. 이 작업은 아직 Compose 전용
명령이 없어 호스트에 uv와 Node 24(Corepack)가 있을 때 실행합니다.

```bash
uv run --project apps/trend-api --locked python apps/trend-api/scripts/export_schema.py
corepack pnpm --dir apps/trend-web install --frozen-lockfile
corepack pnpm --dir apps/trend-web contract
```

첫 명령은 `apps/trend-web/lib/contract/schema.json`을 쓰고, 마지막 명령은 `types.ts`를 생성합니다.
`types.ts`는 손으로 고치지 않습니다. 생성된 두 파일을 `schemas.py` 변경과 같은 커밋에 넣으세요.

## 로컬 Gemma 연결

기본 `up -d`와 `check`는 모델을 호출하지 않습니다. 번역·재작성·분류 단계에 로컬 Gemma를 쓰려면
Mac 호스트에서 Ollama를 켜고 API 컨테이너에 주소를 알려 줍니다.

```bash
brew install ollama
OLLAMA_NO_CLOUD=1 OLLAMA_HOST=127.0.0.1:11434 ollama serve
ollama pull gemma4:e4b
```

컨테이너에서 호스트 Ollama에 닿는 주소는 `http://host.docker.internal:11434`입니다.
`apps/trend-api/.env.example`의 `GEMMA_LOCAL_MODEL`, `LOCAL_LLM_BASE_URL`, `USE_LOCAL_GEMMA` 설명을 따르고,
Compose에서는 `api` 서비스 환경변수로 같은 값을 넘깁니다. 모델 파일은 `~/.ollama/models`에 있으며 Git이나
Docker 이미지에 넣지 않습니다. 별도 GPU 서버의 vLLM은 [Gemma/vLLM 안내](../../models/vllm/README.md)를 참고하세요.

## 패키지 추가·제거·업데이트

실행 중인 컨테이너에 `exec`로 설치하면 저장소의 목록·lockfile이 바뀌지 않습니다.
아래 전용 명령은 **호스트 저장소에 두 파일을 함께 기록**합니다. 로컬 Node·Python 설치는 필요 없습니다.
반드시 저장소 루트에서 실행하세요.

| 대상 | 함께 커밋할 파일 |
| --- | --- |
| 웹 | `apps/trend-web/package.json`, `apps/trend-web/pnpm-lock.yaml` |
| API | `apps/trend-api/pyproject.toml`, `apps/trend-api/uv.lock` |

다음 패키지명은 사용법 예시입니다. 실제 필요한 패키지로 바꿔 실행하세요.

| 할 일 | 명령어 예시 |
| --- | --- |
| 웹 패키지 추가 | `docker compose run --rm --build pnpm add zod` |
| 웹 개발용 패키지 추가 | `docker compose run --rm --build pnpm add -D prettier` |
| 웹 패키지 제거 | `docker compose run --rm pnpm remove zod` |
| 웹 목록을 직접 수정한 뒤 lockfile 갱신 | `docker compose run --rm pnpm install --lockfile-only` |
| API 패키지 추가 | `docker compose run --rm --build uv add httpx` |
| API 개발용 패키지 추가 | `docker compose run --rm --build uv add --dev pytest` |
| API 패키지 제거 | `docker compose run --rm uv remove httpx` |
| API 패키지의 허용 범위 내 업데이트 | `docker compose run --rm uv lock --upgrade-package httpx` |
| API 목록을 직접 수정한 뒤 lockfile 갱신 | `docker compose run --rm uv lock` |

`pnpm`·`uv` 도구 서비스는 해당 앱 폴더만 컨테이너에 연결하므로 다른 앱이나 `prototype/`은 수정하지 않습니다.
여러 패키지 수정 명령을 동시에 실행하지 말고 하나씩 완료하세요. 패키지 제거는 사용처도 수정해야 합니다.

변경 후에는 차이를 확인하고 이미지를 재빌드합니다.

```bash
git diff -- apps/trend-api/pyproject.toml apps/trend-api/uv.lock apps/trend-web/package.json apps/trend-web/pnpm-lock.yaml
docker compose up -d --build
docker compose run --rm --build check
docker compose run --rm --build e2e
```

검증이 통과하면 변경한 목록과 lockfile을 **같은 커밋**에 포함하세요.
lockfile의 버전이나 해시는 손으로 편집하지 않습니다. 빌드는 `pnpm install --frozen-lockfile`과 `uv sync --locked`로
목록·lockfile 불일치를 거부합니다. 명령 실패 시 일부 파일이 바뀌었을 수 있으므로 `git diff`를 확인하세요.

## 자주 쓰는 작업 순서

다음 날 작업을 시작할 때는 Docker를 켜고 저장소 루트에서 실행합니다.

```bash
docker compose up -d
```

팀의 최신 변경을 받을 때는 먼저 `git status`로 본인의 수정 내역을 확인합니다.
수정한 파일을 정리한 뒤 다음을 실행하세요.

```bash
git pull --ff-only
docker compose up -d --build
```

코드 변경을 공유하기 전에는 다음을 실행합니다. 첫 번째 명령이 실패하면 원인을 해결한 뒤 진행하세요.

```bash
docker compose run --rm --build check
docker compose run --rm --build e2e
```

작업이 끝나면 `docker compose down`으로 종료합니다.

## 옵션과 파일 역할

| 항목 | 의미 |
| --- | --- |
| `-d` | 터미널을 점유하지 않고 백그라운드 실행 |
| `--build` | 실행 전에 이미지 빌드, 바뀌지 않은 단계는 캐시 재사용 |
| `--rm` | 일회성 작업 컨테이너를 종료 후 제거 |
| `--wait` | 서비스가 실행·정상 상태가 될 때까지 대기 |
| `-f` (`logs`에서) | 새 로그를 계속 표시 |
| `compose.yaml` | 팀원과 CI가 실행하는 서비스·검증 명령 정의 |
| `apps/trend-web/package.json` | 컨테이너 내부의 웹 도구 명령 |
| `apps/trend-api/scripts/` | 파이프라인·사전 점검·계정 생성·SQLite 이관 등 API 쪽 작업 도구 |
| `scripts/` | 릴리스·smoke 검사·배포·롤백의 내부 구현, [파일별 역할](../../scripts/README.md) |

`scripts/bootstrap-gcp.sh`, 배포·롤백 스크립트, `release/gcp` push는 운영 명령입니다.
평소 개발에서는 실행하지 말고 실제 배포 시 [운영 문서](../운영/GCP-운영.md)를 따릅니다.

## GitHub CI는 언제 실행되나요?

- `develop` push와 PR은 자동 검증을 실행하지 않습니다.
- `release/gcp` push는 변경 범위를 판정합니다. 코드 변경은 공통 CI를 한 번, Terraform만 변경된 경우 인프라 검사만 실행합니다.
- 문서나 `prototype/`만 바뀌면 검사·배포 job을 실행하지 않습니다. `apps/alert-relay`가 바뀌면 공통 CI 뒤 중계기 배포 job이 실행됩니다.
- `apps/trend-api`·`apps/trend-web` 변경은 공통 CI만 실행합니다. Trend 앱 배포 job은 [Plan 05](../plans/archive/05-trend-cloud-run-deployment.md)가 끝날 때까지 꺼져 있습니다.
- GitHub Actions의 CI 화면에서 `Run workflow`로 수동 실행할 수도 있습니다.
- 배포 job은 `gcp` environment를 사용하며 진행 중인 배포를 새 push로 취소하지 않습니다.

`verify`는 작업 이름입니다. 그 안에서 `check`·실제 서비스 의존성 검사·브라우저 테스트·Terraform 검증·
Trend API·웹 배포 이미지 빌드·컨테이너 smoke 검사·알림 중계기 이미지 검사를 실행합니다.

팀원의 PC가 Mac이어도 CI는 Docker의 Linux 실행 환경을 확인하므로 Ubuntu runner를 사용합니다.
공개 저장소의 표준 runner는 무료이고, 비공개 저장소는 소유자 계정의 요금제별 무료 시간을 사용합니다.
GitHub Free 기준 월 2,000분이며 다른 비공개 저장소 사용량과 공유됩니다.
[공식 Actions 과금 안내](https://docs.github.com/en/billing/concepts/product-billing/github-actions)를 기준으로,
GitHub 계정의 Billing and licensing에서 실제 사용량과 예산·초과 사용 차단 설정을 확인하세요.
이 저장소의 CI 설정만으로 계정 전체의 과금을 막지는 못합니다.
