작성일은 **2026-09-19**, 최종 실습 기록일은 **2026-09-20**입니다.
완료한 단계는 검증 결과를 기록하고, 나머지는 앞으로 진행할 계획으로 구분합니다.
PostgreSQL 1단계와 그래프 워크플로우 2단계는 구현·검증했습니다. 실행 이력 저장과 실제 모델 연결은 아직 미착수입니다.

## 실습 목적과 범위

주제 선정 전에 DB 영속성, 모델 호출, 그래프 실행, 오류 처리와 실행 기록을 작은 예제로 익힙니다.
최종 서비스의 도메인 테이블이나 기능을 미리 확정하지 않습니다.
기존 웹·API와 Compose 명령 체계를 활용하고 첫 단계는 Mock으로 재현 가능하게 만듭니다.

| --- | --- | --- |
| 1 | PostgreSQL 연결과 데이터 유지 | 완료 — 2026-09-20 |
| 2 | 입력 검사·Fan-out·Join·규칙 Router | 완료 — 2026-09-20 |

## 사용자가 지금 준비할 것

**1~4단계에는 API 키, 유료 계정, 최종 주제, 그래프 DB가 필요하지 않습니다.**

| 준비 항목 | 사용자가 할 일 | 없을 때의 진행 방법 |
| --- | --- | --- |
| Docker Desktop | 실습할 때 앱을 켜고 엔진 실행 상태 확인 | 설치 자체는 기존 가이드 사용 |
| 샘플 문서 | 있으면 공개·비식별 문서 3~5개와 기대 결과 제공 | 합성 문서를 만들어 시작 |
| 보고 싶은 결과 | 예를 들어 요약과 핵심 항목이라고 알려주면 됨 | 기존 요약·핵심 항목 형식 사용 |
| 실패 사례 | 잘못된 답변으로 간주할 예시가 있으면 제공 | 지연·형식 오류·필수 정보 누락으로 시작 |
| 실습 데이터 보관 | 첫 실습은 합성 입력과 실행 메타데이터 사용 | 실제 업무 데이터 없이 진행 |

샘플을 제공한다면 문서마다 "기대 요약", "반드시 남겨야 할 항목", "만들어내면 안 되는 사실"을
짧게 적어 주세요. 정답을 완벽히 작성할 필요는 없습니다. 판단 기준을 공유하는 것이 목적입니다.
키나 비밀번호는 채팅·Issue·저장소에 붙여넣지 않습니다.

DB 이미지·포트·접속 계정, 초기 스키마 변경 절차, 테스트와 Compose 구성은 구현 단계에서 준비할 수 있습니다.
사용자가 직접 SQL이나 에이전트 코드를 작성해서 가져올 필요는 없습니다.

## 1단계 — PostgreSQL 연결과 영속성

Compose에 PostgreSQL 18.6과 영속 볼륨, 접속 설정, 반복 가능한 초기 스키마 준비를 구현했습니다.
기존 Mock 요약 기능과 별개로 `lab.records`에 합성 실습 기록만 저장합니다.

완료 기준:

- DB가 준비된 후 API가 연결되고 간단한 저장·조회가 된다.
- 초기 스키마를 새로운 DB에서 재현할 수 있다.
- 컨테이너 재시작 후 같은 레코드가 조회된다.
- 볼륨을 유지한 컨테이너 제거·재생성 후에도 레코드가 유지된다.
- DB가 꺼졌거나 연결이 실패하면 오류를 명확하게 보여 준다.

영속성 확인을 위해 볼륨을 지우는 명령을 사용하지 않습니다.
볼륨 보존과 백업은 별개이므로, 첫 실습에서 백업·복구까지 완료했다고 간주하지 않습니다.

### 직접 실행해 보기

```bash
docker compose up -d --wait
docker compose run --rm db-check
```

문서 입력 없이 `PostgreSQL persistence exercise`라는 기록을 생성합니다.
결과에는 UUID인 `id`, 기록 이름인 `label`, 생성 시각인 `created_at`이 표시됩니다.
출력된 `Read again` 명령과 `Open` 주소는 기존 기록을 조회하는 방법입니다.
DB 전용 웹 화면을 만든 것은 아니며, http://localhost:8000/docs 의 실습 API나 출력된 주소로 확인합니다.

```bash
docker compose restart db
```

재시작 후 출력해 둔 `Read again` 명령을 다시 실행해서 같은 기록인지 비교합니다.
`db-check` 기본 명령을 새로 실행하면 새 기록이 생기므로 영속성 비교에는 기존 ID를 사용합니다.

### 검증 기록 — 2026-09-20

구현 커밋은 [`eb2faf6`](https://github.com/Sihyeon-Ji/2026-google-ai-builder-cup/commit/eb2faf6)입니다.

검증한 레코드는 `64125a24-d558-4100-961b-0816bdc8fe20`이며 생성 시각은
`2026-09-19T23:24:53.188018Z`입니다. 이 ID는 검증 PC의 볼륨에만 존재합니다.
다른 PC에서는 `db-check`로 새 ID를 생성해서 실습합니다.

초기 개발 중 비밀번호 생성용 `umask`가 PostgreSQL 디렉터리 생성에도 적용되어 기동이 실패했습니다.
비밀번호 생성 후 `umask 022`로 복원하도록 수정하고, 별도의 빈 볼륨에서 처음부터 정상 기동을 확인했습니다.
임시 검증용 컨테이너·볼륨만 정리했으며 개발용 기록과 비밀번호 볼륨은 유지했습니다.

초기화 코드는 기존 테이블을 자동 변경하는 범용 마이그레이션 도구가 아닙니다.
이후 열·제약 변경은 기존 데이터를 보존하는 명시적 마이그레이션으로 추가합니다.
원격 DB와 실제 모델 연결은 이번 단계의 검증 범위에 포함되지 않습니다.

## 2단계 — 작은 샘플 워크플로우

합성 문서 하나를 받아 요약·핵심 항목을 추출하는 분기와 문자 수·필수 헤더를 검사하는 분기를
병렬 실행합니다. 결과를 정해진 구조로 합치고, 규칙에 따라 통과 또는 보완 필요로 분기합니다.

완료 기준:

- 빈 입력이나 제한 초과 입력은 모델 호출 전에 거부한다.
- 병렬 단계는 서로의 결과에 의존하지 않는다.
- Join은 모든 필수 결과의 존재와 형식을 검사한다.
- Router의 통과·실패 조건을 모델 호출 없이 테스트할 수 있다.
- 노드별 상태와 실행 순서를 확인할 수 있다.

학습용 첫 버전은 일반 Python과 `asyncio`로 구현했습니다. 기존 모델 호출 함수를 재사용하며
그래프 DB나 에이전트 프레임워크는 필요하지 않습니다. 이후 지속성·복잡한 분기가 필요해지면
ADK나 LangGraph를 검토합니다. 자체 범용 그래프 엔진은 만들지 않습니다.

### 직접 실행해 보기

```bash
docker compose run --rm --build workflow-check
```

기본 합성 문서는 다음과 같습니다.

```text
## 일정
팀 회의는 금요일 오후 3시에 진행한다.
## 준비
발표 자료는 목요일까지 준비한다.
## 담당자
발표 담당자는 아직 정하지 않았다.
```

실행은 `입력 검사 → [Mock 추출, 문서 규칙 검사] → Join → Router` 순서입니다.
대괄호 안의 두 작업은 독립적으로 스케줄링되며, 둘 다 끝나야 Join과 Router가 실행됩니다.
Mock은 실제 요약 모델이 아니라 원문의 일부로 정해진 형식을 채우는 대역입니다.

| 입력 | 기대 결과 | 검증 결과 |
| --- | --- | --- |
| 일정·준비 제목과 내용이 모두 있음 | `accepted` | 통과 |
| 준비 제목이 없음 | `needs_revision`, `missing_required_sections` | 통과 |
| 준비 제목만 있고 내용이 없음 | `needs_revision`, `empty_required_sections` | 통과 |
| 빈 입력·공백·최대 길이 초과 | 모델 호출 전에 거부 | 통과 |

`accepted`는 두 필수 제목에 내용이 있는지를 통과했다는 뜻입니다. 일정이 실제로 맞는지,
담당자가 누구인지, 모델 답변이 정확한지를 판정하는 것은 아닙니다.
`## `로 시작하는 제목만 인식하는 작은 실습 규칙이며 일반 Markdown 해석기가 아닙니다.

API 경로는 `POST /api/lab/workflow`입니다. http://localhost:8000/docs 에서 다음 입력을 보낼 수 있습니다.

```json
{"text":"## 일정\n금요일 오후 3시 팀 회의\n## 준비\n목요일까지 발표 자료 준비"}
```

응답의 `analysis`는 기존 모델 응답 형식, `document_checks`는 문자 수와 누락·빈 항목,
`decision`은 규칙 판단, `events`는 노드의 시작·완료 순서입니다.
한쪽 필수 분기가 실패하면 정상 Join 결과를 만들지 않고 남은 비동기 작업을 취소합니다.
실패한 실행의 상세 이력 저장과 사용자용 실패 시나리오 실행은 3·4단계에서 다룹니다.

### 검증 기록 — 2026-09-20

- API에서 합성 문서 3종과 공백 입력 검증을 통과했습니다.
- 모델 분기가 문서 검사의 시작을 기다리도록 만든 테스트로 두 분기의 동시 스케줄링을 검증했습니다.
- 두 분기가 모두 완료된 뒤에만 Join, 이후 Router가 실행되는 것을 검증했습니다.
- 잘못된 모델 JSON은 정상 결과로 전달하지 않고, 검사 분기 실패 시 대기 중인 모델 작업을 취소합니다.
- DB 실습을 비활성화한 앱에서도 워크플로우 API가 동작합니다.
- 실습 API는 기본·배포 미리보기에서 꺼져 있고 Cloud Run에서는 활성화를 거부합니다.

구현 커밋은 [`69b8b74`](https://github.com/Sihyeon-Ji/2026-google-ai-builder-cup/commit/69b8b74)입니다.
전체 Python 테스트 23개, 기존 브라우저 테스트 2개와 배포 이미지 smoke test가 통과했습니다.

현재 Mock 응답은 즉시 완료되므로 콘솔에서 두 분기가 차례로 끝나 보일 수 있습니다.
콘솔 순서만 보고 병렬 성능을 측정한 것으로 해석하지 않습니다. 단계별 시간·실행 이력의 DB 저장은
아직 구현하지 않았으며, 모든 실습 결과는 요청 응답에만 포함됩니다.

## 3단계 — 실행 이력 조회

실행 하나와 그 안의 단계들을 연결해 저장하고, 실행 목록 및 상세를 조회하는 최소 화면이나 API를 제공합니다.

| 기록할 정보 | 용도 |
| --- | --- |
| 실행 ID·노드 ID | 실패 단계 추적 |
| 실행 순서와 상태 | 대기·실행·완료·실패 구분 |
| 시작·종료 시각과 소요 시간 | 병목 확인 |
| Provider·모델·프롬프트 버전 | 결과 비교 조건 확인 |
| 입력·출력 토큰 | 실제 모델 사용량 비교 |
| 오류 코드·재시도 횟수 | 오류 원인과 반복 확인 |

완료 기준:

- 실행 목록에서 성공과 실패를 구분하고 상세 단계로 들어갈 수 있다.
- 실행과 각 단계의 관계가 DB에서 일관되게 유지된다.
- 메타데이터를 컨테이너 재시작 후에도 조회할 수 있다.
- 공급자가 토큰 수를 제공하지 않으면 미확인으로 표시한다. 추정치와 실제 값을 구분한다.
- 원문·생성 결과·인증정보가 운영 로그에 기록되지 않는다.

이력 저장만으로 작업 중단 후 자동 재개가 완성되는 것은 아닙니다. 첫 단계에서는 중단·실패를
어떻게 표시할지 정의하며, 영속 체크포인트 기반 재개는 별도 요구가 생기면 확장합니다.

| 재현할 상황 | 기대 동작 |
| --- | --- |
| 모델 응답 지연 | 정해진 시간 안에 종료하고 timeout 기록 |
| JSON 문법 또는 결과 형식 오류 | 정상 결과로 통과시키지 않고 실패 표시 |
| 병렬 분기 중 하나 실패 | 정해 둔 실패 정책대로 종료, 누락 결과로 성공 처리하지 않음 |
| 일시적 연결 실패 | 허용 횟수까지만 재시도 |
| DB 기록 실패 | 성공 응답과 기록 정책이 어긋나지 않도록 정의·검증 |

첫 실습의 기본 제안은 필수 분기 중 하나라도 실패하면 전체를 실패로 기록하는 것입니다.
부분 결과 반환이 필요해지면 별도 상태와 사용자 표시를 설계합니다.
Mock 실패를 사용해 반복 가능한 테스트를 만들고, 무제한 재시도·무제한 모델 루프를 두지 않습니다.

## 5단계 — 실제 모델로 교체하고 비교

이 단계에서만 다음 사항을 정하면 됩니다.

| 선택 | 필요한 준비 | 현재 권장 방향 |
| --- | --- | --- |
| Mac 로컬 모델 | 런타임 설치, 모델·라이선스 확인, 파일 다운로드, 메모리·디스크 점검 | Ollama와 작은 모델 하나로 먼저 실습 |
| 원격 Gemini | 인증정보, 모델 접근·할당량, 비용 범위 | GCP 보류가 해제된 후 별도 준비 |

모델 크기와 정확한 버전은 아직 정하지 않았습니다. 설치할 런타임의 API 호환성 및 모델의
한국어 처리·구조화 출력 지원을 확인하고 선택합니다. GPU가 필요한 부분은 Mac 호스트에서 실행하는 구성이 후보입니다.

완료 기준:

- 같은 샘플 입력과 같은 결과 형식으로 Mock과 실제 모델을 실행한다.
- 모델 연결 실패를 Mock 성공으로 바꾸지 않는다.
- 형식 통과 여부와 내용 품질을 별도로 평가한다.
- 중요한 항목의 누락·허위 추가·소요 시간·토큰 사용량을 비교한다.
- 초기 로딩 시간과 이후 요청 시간을 구분하고 사용한 모델·설정을 기록한다.
- Mock 결과를 AI 품질의 기준 정답으로 취급하지 않는다.

사용자가 알려주면 유용한 선호는 "우선 로컬만 사용할지", "한국어 위주인지", "속도와 품질 중 무엇이 중요한지"입니다.
지금 답을 모두 정할 필요는 없습니다. 1~4단계를 진행하는 데 결제수단이나 모델 계정은 필요하지 않습니다.

## 실습 기록을 남기는 방식

각 단계가 실제로 끝나면 이 문서의 상태와 함께 다음 증거를 기록합니다.

- 실행한 커밋·날짜와 명령
- 기대 결과와 실제 결과, 통과·실패 여부
- 합성 테스트 케이스와 해결한 문제
- 재시작·재실행 후 확인 결과
- 실제 모델을 사용했다면 모델·설정·품질 평가 결과

재현 가능한 코드·테스트·명령은 저장소에, 실제 비밀정보와 모델 가중치는 Git 밖에 둡니다.
DB·모델 서비스가 구현된 이후에만 해당 실행 명령을 [명령어 모음](commands.md)에 추가합니다.
PostgreSQL과 작은 그래프 워크플로우 실습은 완료했습니다. 실행 이력의 DB 저장과 Ollama 연결은 아직 미착수입니다.
